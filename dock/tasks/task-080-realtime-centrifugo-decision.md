# task-080 — решение о real-time доставке чата

Статус: черновик, ждёт одобрения владельца.
⚠️ Обоснование ниже УСТАРЕЛО (сверено 24.09.2026): умножение запросов к базе
на число слушателей убрано планами 067, 085 и 092 — цена события не растёт
ни с числом вкладок, ни от того, смотрят ли все один чат. Осталась другая
причина — задержка событийного цикла единственного процесса до 0,969 с
при 3000 вкладках. Решение принимается после профиля и замера на тихой
машине ([Д-55](../debt.md#d-55)).
Перенесённый опыт по граблям: [шишки живых обновлений](../reference/шишки-живых-обновлений-2026-09.md)
и скилл `.claude/skills/centrifugo-realtime/`.
Риск: высокий — меняется клиент-серверный протокол, модель прав и состав инфраструктуры.
Заведено: 2026-09-13

## Зачем

Текущий поток SSE говорит всем вкладкам пространства только «что-то изменилось».
Каждая вкладка затем вызывает `/v1/sync`; тот возвращает реплики всего
пространства, хотя клиент показывает текст лишь открытого разговора. При цели
5000–10000 одновременно активных людей это умножает сетевой и SQL-трафик на
число слушателей и не даёт точной доставки по разговору.

Предварительное направление владельца: отдельный real-time слой на Centrifugo
с WebSocket. Решение не означает немедленно добавлять Redis, кластер,
Kubernetes или заменять PostgreSQL: их необходимость определяется измеренной
нагрузкой и числом real-time узлов.

## Что принять до кода

1. PostgreSQL остаётся единственным источником истины для сообщений, прав и
   истории. Сообщение сначала фиксируется транзакцией, затем публикуется в
   real-time слой.
2. Centrifugo отвечает только за быструю доставку онлайн-клиентам: каналы,
   соединения, переподключение и короткое восстановление. Его история не
   заменяет историю сообщений в PostgreSQL.
3. HTTP-страницы разговоров остаются способом первичной загрузки и запасным
   путём восстановления. `/v1/sync` переосмысливается после отдельного
   контракта, а не удаляется вслепую.
4. События разделяются по назначению: открытый разговор получает полную
   реплику; неоткрытые доступные разговоры получают только данные, нужные для
   списка (unread, последнее изменение, при необходимости preview).
5. Права проверяются при выдаче права подписки на каждый канал. Клиент не
   выбирает произвольный `chat:<id>` без серверной проверки членства.
6. Один Centrifugo-узел без Redis допустим только как начальная конфигурация.
   Redis становится стандартным broker перед вторым real-time узлом: он даёт
   межузловую доставку и короткую историю для recovery. NATS — отдельная
   развилка лишь для осознанной доставки «не более одного раза» с HTTP fallback;
   решение о втором узле принимается по замеру соединений, CPU, памяти,
   задержки и reconnect-нагрузки.

## Порядок

1. Провести с владельцем учебный разбор: соединение, канал, шина, база,
   cursor/recovery, один и несколько узлов — на сценарии одного сообщения.
2. Сверить выбранную модель с публичными источниками и исходниками Rocket.Chat,
   Tailchat, Spacebar, Socket.IO и Centrifugo; отделить подтверждённое от
   допущений.
3. Записать новое архитектурное решение в `dock/decisions.md` со ссылками:
   почему Centrifugo, почему PostgreSQL остаётся истиной, почему не Socket.IO
   и Supabase Realtime, какие пороги включают Redis и второй узел.
4. Описать внешний контракт в отдельном OpenSpec change: имена каналов,
   payload полных реплик и сводок, выдача токена/подписки, reconnect и fallback
   в HTTP.
5. Сначала написать красные приёмочные сценарии: авторизованный участник
   получает реплику ровно раз; неучастник не подписывается; отключённый клиент
   восстанавливает пропущенное; чужая закрытая комната не выдаёт ни текста,
   ни сводки.
6. Внедрять в малых шагах: локальный Centrifugo без Redis; server-side publish
   после commit; один клиентский канал; затем разделение полных событий и
   сводок; потом измерения и решение о горизонтальном масштабировании.

## Арбитры

- приёмочные тесты через настоящий reverse proxy доказывают доставку, права,
  дедупликацию и HTTP fallback;
- живой прогон: два человека, два разговора, разрыв сети, повторное
  подключение и переключение разговора;
- нагрузочный прогон на засеиваемой базе: 5000 удерживаемых соединений,
  публикации в малый и большой разговор, reconnect-wave;
- метрики: количество соединений, publish-to-client p95, CPU, память,
  ошибки авторизации, recovery success/fallback и SQL-запросы на публикацию.
