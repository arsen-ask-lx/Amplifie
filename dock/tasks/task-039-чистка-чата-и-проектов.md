## 1. Зачем

Владелец 11.09: «приведём весь продуктовый код до состояния идеал и только
потом продолжим добавлять новый функционал… главное не плодить технический
долг».

Полное чтение кода чата 11.09 показало: фундамент верный (счётчик номеров
пространства, мягкое удаление с надгробием, идемпотентная отправка, журнал
в той же транзакции, один путь догона — как у Slack и Matrix), а брак сидит
в «клее» и повторяется КЛАССАМИ:

1. **два ответа на вопрос о правах** — `visibleTo` читает видимость ветки,
   `peopleWhoSee` — корня; ветки приватного канала видит всё пространство
   (task-027 №1, критично);
2. **правило «непрочитано» записано четыре раза** — три на сервере, одно
   на клиенте;
3. **сквозное руками в каждом месте** — вход в 25 обработчиках (и своя копия
   `viewerOf` в `chat.ts`), перевод ошибок в коды в каждом маршруте,
   «транзакция + событие + звонок» в каждой мутации; `createThread` звонок
   забыл;
4. **протокол догона с дырами** — курсор из `seq` вместо `updatedSeq`, один
   номер изменения на много строк при `LIMIT`, обрыв клиента на 20 страницах,
   «прочитано из будущего» (task-027 №3, №4, №11, №5);
5. **контракт не машинный** — обещанный каркасом OpenAPI (`04-каркас.md`:
   «REST + OpenAPI 3.1, генерится из тех же схем, `openapi.json` в git»)
   не сделан; типы ответов написаны руками дважды — на беке и на фронте;
6. **фронт сам изобретает кеш серверных данных** — `useChat` 671 строка,
   25 полей наружу, ручные загрузки и отмены;
7. **комментарии размером с код и врут** — истории инцидентов в коде,
   за сессию найдено больше десятка оторванных и лгущих, два прямо
   оправдывают баги;
8. **оснастка молча сломана** — снимки схемы drizzle кончаются на 0016
   при миграциях до 0024; гейты, в том числе мёртвый код, не запускаются
   под Windows; N+1 сторожится только для одного запроса панели.

Латать экземпляры бессмысленно: следующая функция родит те же баги. Чиним швы.

## 3. Как делаем

Шаг за шагом, каждый — отдельный коммит; сначала красный тест, потом правка,
после шага прогон. После любого шага можно остановиться с рабочим продуктом.

**Правило каждого шага: сперва ищем готовое.** Где есть стандартное решение
(плагин Fastify, генератор типов, библиотека) — берём его; своё пишем,
только когда готового нет или оно дороже. Выбор новой зависимости —
по правилу проекта: веб-ресёрч и запись в `dock/decisions/` со ссылками.

**Чего не трогаем:** агентов и доску (владелец: «мы их по сути ещё не делали»),
кроме того, что общее с чатом (двери, контракт). `tmp/`, `shared/theme.ts`,
`themes.css` — работа второго агента.

**Расхождения с принятыми решениями:** расхождений нет — шаг 3 доделывает
обещанное каркасом.

## 4. Шаги

1. **Одна видимость, одно правило «непрочитано».** Права читаются только
   у корня одной функцией; «кто видит разговор» выводится из неё же;
   правило «дальше номера прочтения» — одно выражение на три запроса.
   - файлы: `talk/repo.ts`, `talk/mentions.ts`, `talk/unread.ts`, `talk/service.ts`
   - проверка: приёмочный «ветка приватного канала не видна постороннему»
     (красный до правки) + парный «участнику видна»
2. **Сквозное на сервере — в одном месте.** Вход — хуком Fastify; отказы
   ядра → коды — общим обработчиком ошибок; мутация — одной обёрткой
   «транзакция, событие, звонок после фиксации».
   - файлы: `surface/http/*`, `talk/service.ts`, `talk/projects.ts`, `talk/pins.ts`
   - проверка: приёмочные зелёные без правки; новый — «ветка появляется
     у соседа без перезагрузки»
3. **Контракт — OpenAPI из zod-схем.** Схемы запросов И ответов на дверях
   чата; `openapi.json` в git; типы фронта генерируются из него вместо
   ручных; гейт «`openapi.json` не отстал от кода».
   - файлы: `surface/http/*`, `frontend/src/data/api.ts`, `packages/contract`, `tools/checks/`
   - проверка: гейт падает на подсаженном расхождении; `make typecheck`
4. **Правильный догон.** Составной курсор (номер изменения, id); отметка
   прочтения не дальше головы; клиент догоняет до конца без обрыва.
   - файлы: `talk/repo.ts`, `talk/service.ts`, `data/useChat.ts`
   - проверка: приёмочные на триггеры task-027 №3, №4, №5; модульный на №11
5. **Бюджет запросов к базе на один запрос HTTP (N+1).** Счёт запросов
   на каждый обработанный запрос; приёмочные падают, если дверь превысила
   бюджет; гейт цены остаётся для объёма.
   - файлы: `platform/db.ts`, `surface/http/app.ts`, `backend/tests/`
   - проверка: подсаженный N+1 роняет проверку
6. **Разрезать `useChat`.** Решение со ссылками: TanStack Query для
   запрос-ответных данных (панель, закреплённое, люди) против своего;
   лента с курсором остаётся своей.
   - файлы: `frontend/src/data/*`, решение в `dock/decisions/`
   - проверка: сценарии интерфейса зелёные
7. **Комментарии и имена.** Правило в `.temper/rules/`: в коде — короткое
   «почему», история — в `dock/`; имена в коде — только латиницей (русский —
   в текстах интерфейса, комментариях, названиях тестов). Проход по файлам
   чата; ~200 кириллических имён переименовываются; когда их ноль — включается
   правило Biome `useNamingConvention` с `requireAscii` (готовое, не своё).
   Гейта на долю комментариев нет (Гудхарт).
   - проверка: чтение; ни одного утверждения, противоречащего коду; линтер
     не пропускает кириллицу в имени
8. **Оснастка.** Снимки drizzle догнать до схемы; линтер не смотрит в `tmp/`;
   гейты запускаются Git Bash; мёртвый код, повторы и OpenAPI — в `make check`
   и CI обязательно.
   - проверка: `make check` зелёный на Windows без WSL

## 5. Признаки приёмки

- П-1: на вопрос «кто видит разговор» в коде один ответ; ветка приватного
  канала постороннему не видна.
- П-2: новая мутация не может забыть звонок или событие — их ставит обёртка.
- П-3: догон не теряет и не повторяет строки на границе страницы.
- П-4: типы ответов фронта сгенерированы из `openapi.json`, ручных копий нет.
- П-5: подсаженный N+1 роняет проверку.
- П-6: `make check`, `make test`, `make test-ui` зелёные на машине владельца.

## 6. Вопросы к тестам

- В-1: «приватная ветка не видна постороннему, видна участнику» — 2 теста
- В-2: «ветка появляется у соседа без перезагрузки» — 1 тест
- В-3: «догон на границе страницы: правка старой, удаление с ответами,
  отметка из будущего» — 3 теста
- В-4: «дверь сверх бюджета запросов роняет проверку» — 1 тест

**Бюджет:** ~10 новых тестов; остальное держат существующие 199.

## 7. Границы

- менять: ядро чата, двери HTTP, слой данных фронта, контракт, оснастку проверок
- не трогать: `agent/*`, `app/answering|working|doing|agents|bridging`, `kernel/work`,
  `tmp/`, `shared/theme.ts`, `themes.css`
- коммиты — только по явным путям: владелец правит параллельно

## 8. Арбитр

- тесты: В-1…В-4 красные до правки; существующие приёмочные и сценарии
  зелёные после каждого шага;
- гейты: мёртвый код, повторы, OpenAPI, бюджет запросов — в `make check`;
- живой прогон: два браузера, приватный канал, отставшая вкладка.

## 9. Наблюдаемость

- исход: отказ ядра → стабильный код из одного места;
- события: ставит обёртка мутации, забыть нельзя;
- повтор: догон и отметка прочтения проверяются повтором того же запроса.

## 10. Риски

- правка прав отрежет законный доступ → на каждое «нельзя» парное «можно»;
- новая зависимость (OpenAPI, TanStack) окажется тяжелее своего → ресёрч
  и запись решения до кода; при сомнении — не берём;
- пересечение с правками владельца → перечитывать файл перед правкой,
  коммитить по путям.
