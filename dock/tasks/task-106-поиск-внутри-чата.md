## За 60 секунд

- **Сейчас:** поиск один — Ctrl+K по всем видимым чатам. Внутри чата искать
  нечем; лупа в шапке открывает то же общее окно.
- **После (решение владельца 17.09 «как в Telegram, оба»):**
  - **лупа в шапке и Ctrl+F** открывают поиск **в открытом чате**: полоса под
    шапкой с полем, счётчиком «3 из 17» и стрелками вверх-вниз;
  - стрелки ходят по попаданиям, подсвечивая каждое; Escape закрывает полосу;
  - **Ctrl+K остаётся общим** поиском по всем чатам, как есть.
- **Бесшовно:** переход между соседними попаданиями **не перезагружает ленту**,
  если реплика уже в загруженном окне — только прокрутка и одна вспышка.
  Сейчас каждый переход по адресу грузит окно заново.
- **Цена названа числами (замер 18.09 на 200 тыс. реплик, базе
  `amplifie_search_room`):** поиск частого слова в МАЛЕНЬКОМ чате без нового
  индекса — **11 704 буфера** (обход почти всей таблицы поиска), с индексом
  `(conversation_id, seq)` — **24**; в большом чате — 102; подсчёт «всего»
  с потолком 1000 — 24 и 447. Поэтому в плане миграция с индексом, а не
  «потом посмотрим».
- **Чего НЕ делаем:** поиск по датам и по автору («от кого», «за месяц»
  у Telegram есть — у нас порога нет); подсветку всех попаданий сразу в ленте;
  историю запросов.
- **Как показать без кода:** открыть чат, нажать Ctrl+F, набрать слово —
  видно «1 из N», стрелка вниз ведёт к следующему, лента не мигает.

## 1. Зачем

Решение владельца 17.09: «как в тг, оба» — лупа и Ctrl+F ищут внутри чата,
Ctrl+K по всем. Разбор Telegram Desktop (DeepWiki, 18.09): счётчик «N of
AMOUNT» рисует `BottomBar`, `AMOUNT` приходит с сервера, пусто — если «всего»
неизвестно; стрелки двигают номер и подгружают следующую страницу, когда
номер подходит к концу загруженного (`ComposeSearch`, `Api::MessagesSearch`).
Берём эту же схему.

## 2. Что уже есть

Прочитано целиком: `packages/contract/src/api.ts` (двери поиска),
`backend/src/kernel/talk/search.ts`, `repo.searchMessagesPage`,
`routes/chat.ts` (дверь поиска и предел частоты), `frontend/src/data/useSearch.ts`,
`SearchDialog.tsx`, `ChatScreen.tsx`, `useChat.ts` (эффект загрузки ленты),
`feedScroll.ts` (фокус и подсветка), `tools/checks/check-cost.mjs`.

- дверь `POST /v1/search/messages` уже умеет слова, права и страницы
  по курсору; **фильтра по чату и счётчика «всего» у неё нет**;
- таблица `message_search` имеет GIN по `doc` и btree `(workspace_id, seq)`;
  **индекса по `(conversation_id, seq)` нет** — отсюда 11 704 буфера;
- переход к реплике и одна вспышка подсветки уже сделаны (task-099, task-101);
  **но каждый переход перезагружает окно ленты** — для стрелок это лишнее;
- `useSearch` умеет паузу, отмену и память страниц — переиспользуем с новым
  параметром «в каком чате».

## 3. Как делаем

1. **Дверь:** `searchBody` получает необязательный `conversationId`;
   ответ — необязательный `total` (число попаданий, потолок 1000; больше —
   `1000` и признак «есть ещё»). `total` считается **только для поиска
   в чате**: у общего окна его никто не показывает, а лишний запрос стоит
   буферов.
2. **Запрос:** `repo.searchMessagesPage` получает фильтр по чату;
   рядом — `repo.countMatches` с `LIMIT 1000` в подзапросе.
3. **Миграция 0029:** индекс `(conversation_id, seq)` на `message_search`.
   Строится `CONCURRENTLY`? Нет — таблица у заказчика пустая или мелкая,
   а на нашей базе замера индекс собрался за секунды; простая `CREATE INDEX`
   под общим замком миграции (Р-016, как все прежние).
4. **Полоса поиска в чате** (`ChatSearchBar`): общее поле команды
   (`command-field.tsx`), счётчик «3 из 17», две стрелки, крестик. Живёт
   под шапкой чата, а не окном: окно закрыло бы саму ленту, по которой ходят.
5. **Ход по попаданиям:** стрелка меняет номер; номер подходит к концу
   загруженных — просим следующую страницу (как Telegram). Переход к реплике —
   тем же адресом, что цитата (`openAt`).
6. **Лента не перезагружается зря:** в `useChat` правило «этот номер уже
   в загруженном окне — не грузим заново, только ведём взгляд». Это и есть
   «бесшовно»: между соседними попаданиями лента стоит, работает прокрутка
   и подсветка.
7. **Гейт цены** (`check-cost.mjs`): поиск частого слова **в маленьком чате**
   встаёт в гейт с потолком по прочитанным строкам — иначе индекс однажды
   уронят, и никто не заметит.

**Отвергнуто:**
- считать «всего» без потолка — на частом слове это чтение всех попаданий;
- показывать «N из ∞» — у Telegram при неизвестном числе счётчик пуст, и это
  честнее выдуманного числа;
- окно поиска вместо полосы — оно закрывает ленту, по которой ходишь;
- подсветить все попадания в ленте — у нас окно 300 реплик и вытеснение
  сверху: подсветка жила бы только в видимом куске и врала бы про остальное.

## 5. Признаки приёмки — чем докажем

- **П-1 дверь ищет в чате:** `POST /v1/search/messages` с `conversationId`
  отдаёт только реплики этого чата и `total`; без `conversationId` ответ
  как раньше, `total` отсутствует. Покрасит: потерянный фильтр.
- **П-2 счётчик и стрелки:** в чате с 17 попаданиями видно «1 из 17»;
  стрелка вниз даёт «2 из 17» и подсвечивает вторую реплику; на последнем
  стрелка вниз не ломает счётчик. Проверяется текстом на экране и номером
  подсвеченной реплики (`data-seq`).
- **П-3 бесшовно:** переход между двумя попаданиями, лежащими в одном окне
  ленты, **не даёт ни одного запроса** `GET /conversations/:id/messages`
  (журнал запросов сценария) и даёт ровно одну вспышку подсветки.
  Покрасит: сегодняшнее поведение — перезагрузка окна на каждый переход.
- **П-4 цена:** гейт `make cost` — поиск частого слова в маленьком чате
  читает не больше 400 строк; без индекса гейт красный (замер 18.09:
  11 704 буфера против 24).
- **П-5 Ctrl+K не тронут:** общий поиск по-прежнему находит в других чатах
  (сценарий task-100 зелёный без правок).
- **П-6:** регрессия зелёная; `make check` без новых красных.

**Числа до кода:** RED по двери `search/messages` — 1 (новое поле ответа);
цена: страница поиска в чате 24–102 буфера, подсчёт «всего» 24–447; лента
при ходе по попаданиям внутри окна — 0 запросов. SLO строкой: стрелка
по попаданиям отвечает без обращения к серверу, пока попадания в окне.

## 10. Риски

- **индекс `(conversation_id, seq)` растит запись.** Замер: вставка 200 тыс.
  реплик с тремя индексами заняла 70 с (35 мкс на реплику). Порог пересмотра —
  замер записи из task-100 (158 реплик в секунду) хуже на 20%;
- **`total` с потолком врёт на больших числах** → показываем «1000+»,
  как Telegram показывает пусто при неизвестном; в плане названо;

  попадание рядом, а человек ждёт свежего → правило работает только при
  открытой полосе поиска, и это проверяется сценарием П-3 и регрессией `jump`.
