# task-074-полный-разбор-agent-quality-kit: доказать сторожа и снять диагностику AQK

## 1. Зачем

Владельцу нужен не перечень команд Agent Quality Kit, а понимание, какие из
них полезны Amplifie и что они доказывают на фактическом репозитории. После
обновления до 0.14.0 `doctor` уже сделал инвентаризацию, но не проверил,
ловят ли объявленные сторожа дефект и какие классы брака остаются вне них.

## 2. Что уже есть

- `make aqk` — инвентаризация AQK;
- `make check` — `doctor --run` всех объявленных гейтов;
- `.aqk/` игнорируется git и хранит эфемерные отчёты AQK;
- актуальная версия инструмента закреплена как `0.14.0` в task-073.

## 3. Как делаем

Добавляем отдельные read-only цели `make` для полезных диагностик AQK:
контекста, отчёта, vitals, baseline, prove, probe, prompt, learn и why.
Запускаем их, сохраняем выводы в этой задаче и не применяем предложенные
инструментом изменения автоматически.

**Расхождения с принятыми решениями:** расхождений нет. Команды, создающие
или меняющие правила и настройки (`init`, `start`, `add`, `new`, `badge`,
`context --install`, `note`, `ratchet`), в границы работы не входят.

## 4. Шаги

1. Сверить встроенную справку 0.14.0 и разложить команды на диагностику и запись.
   - файлы: только чтение;
   - проверка: каждая пропущенная команда названа с причиной.
2. Добавить цели `make` для безопасных диагностик.
   - файлы: `Makefile`;
   - проверка: `make help` показывает каждую цель.
3. Запустить `baseline`, `vitals`, `context`, `report`, `prompt`, `learn` и `why`
   для рекомендаций AQK.
   - файлы: только `.aqk/` как игнорируемый отчёт, если команда его создаёт;
   - проверка: у каждой рекомендации есть смысл для Amplifie или причина отказа.
4. Запустить `prove` и `probe`.
   - файлы: только `.aqk/`; `probe` работает в копии дерева;
   - проверка: названы каждый сторож, который ловит или пропускает подсаженный брак.

## 5. Признаки приёмки

- П-1: любая полезная диагностика AQK доступна через `make`;
- П-2: `prove` даёт фактический ответ о доказанности гейтов;
- П-3: `probe` даёт список слепых зон, а не меняет продукт;
- П-4: итог разделяет рекомендации «сделать», «отложить» и «не подходит».

## 6. Вопросы к тестам

- В-1: «новые цели не подменяют версию AQK?»
  - почему важно: локальная диагностика и CI должны использовать один выпуск;
  - как проверим: поиск по `Makefile`;
  - тестов: 0 — статическая сверка закрепления.
- В-2: «сторож действительно ловит дефект?»
  - почему важно: объявленная защита без красного образца декоративна;
  - как проверим: `make aqk-prove`;
  - тестов: 0 — `prove` является арбитром.

**Бюджет:** продуктовых строк нет; добавляются только команды входа в уже используемый инструмент.

## 7. Границы

- читать: официальную документацию 0.14.0, `.aqk.yml`, `AGENTS.md`, текущие отчёты;
- менять: `Makefile`, эту задачу, `dock/README.md`;
- создать: только игнорируемые `.aqk/` отчёты, если их создаёт AQK;
- не трогать: продуктовый код, тесты, `.aqk.yml`, правила, CI, чужие незакоммиченные изменения;
- тесты: только через `make`.

## 8. Арбитр

- `make aqk-prove` — красный и зелёный образец каждого заявленного сторожа;
- `make aqk-probe` — классы брака вне объявленных защит;
- `git diff --check` — изменения ограничены входными командами и журналом задачи.

## 9. Наблюдаемость

Не требуется: диагностика не меняет пользовательское поведение, данные или деньги.
Выводы и коды выхода остаются в логе команд и в итоговом разделе задачи.

## 10. Риски

`probe` окажется пишущим вне `.aqk/` → остановиться, не принимать изменения и назвать
точные файлы. Диагностика предложит новый гейт → не ставить автоматически; сначала
сверить с реальной проблемой Amplifie и существующими сторожами.
