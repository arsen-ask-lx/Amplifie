# task-060-режимы-разработки-и-арбитр-сборки: быстрый Vite отдельно от собранного стенда

Статус: одобрен владельцем 2026-09-11

Заведено: 2026-09-11

## 1. Зачем

При правке CSS или React человек открывает `http://localhost:8477`, меняет файл и
должен увидеть результат от Vite почти сразу. Сейчас `make work` сначала запускает
`make up --build`: это тратит минуты и смешивает два разных режима. А `make test-ui`
может проверить уже работающую, но старую статику Caddy — тест зелёный, а свежий код
в образ не попал.

Пример: после правки анимации панели разработчик запускает `make work`; поднимаются
только база и API, Caddy освобождает `:8477`, Vite показывает новую анимацию. Перед
сдачей `make test-ui` сам пересобирает образ и тестирует именно его.

## 2. Что уже есть

- `Makefile`: `up` собирает весь compose-стенд, но `work` зависит от него; `test-ui`
  только поднимает Caddy без гарантии свежего образа.
- `frontend/vite.config.ts`: Vite уже слушает `:8477`, имеет HMR, polling для Windows
  и прокси на API.
- `compose.yml` и `compose.dev.yml`: Caddy отдаёт собранную статику, API и Postgres
  описаны отдельно; это верное разделение стенда и поставки по Р-030.
- `frontend/Caddyfile`: Caddy проксирует API/SSE и отдаёт статические файлы.
- Р-022 требует проверять UI через собранный образ; Р-030 запрещает смешивать
  клиентскую коробку и локальный dev-стенд.

## 3. Как делаем

Сохраняем Caddy: он нужен как production-like proxy и сервер собранной статики;
переход на Nginx не сделал бы HMR быстрее. `make work` запускает только нужные
сервисы без `--build`, ждёт API и затем передаёт `:8477` Vite. Полная сборка остаётся
явным действием `make up` и обязательной частью `make test-ui`.

Добавляем маленькую диагностическую команду, которая на одном адресе показывает,
кто реально отвечает на `:8477` (Vite или Caddy), и доступен ли API. Источник режима —
ответный заголовок, заданный в конфигурации каждого сервера, а не догадка по процессам.

**Расхождения с принятыми решениями:** расхождений нет. Р-022 сохраняется: UI-тест
всегда проверяет свежий собранный образ. Р-030 сохраняется: базовый compose и Caddy
не заменяются и не получают dev-монтирования.

   - файлы: `Makefile`
   - проверка: `make work` не вызывает `up` и не содержит `--build`; `make up`
     по-прежнему собирает полный стенд.
3. Пометить ответы Vite и Caddy разными безопасными заголовками и добавить
   `make dev-status` без нового сервиса.
   - файлы: `frontend/vite.config.ts`, `frontend/Caddyfile`, новый
     `tools/ops/dev-status.mjs`, `Makefile`
   - проверка: команда явно называет активный режим или понятную причину, почему
     адрес/API недоступны.
4. Сделать `make test-ui` самодостаточным арбитром свежего собранного интерфейса.
   - файлы: `Makefile`
   - проверка: перед Playwright выполнена сборка Caddy-образа; если Vite занял
     порт, команда завершится с понятным отказом, а не проверит dev-экран.
5. Прогнать быстрые проверки и оба живых режима.
   - проверка: `make unit`, `make typecheck`, `make lint`, `make map`, `make openspec`;
     затем `make work` + HMR-проверка и `make test-ui` по Caddy.

## 5. Признаки приёмки

- П-1: `make work` не пересобирает frontend/Caddy-образ и не зависит от `make up`.
- П-2: после `make work` один адрес `:8477` обслуживает Vite, а `/v1` отвечает через
  уже поднятый API.
- П-3: `make dev-status` называет Vite, Caddy или конкретную причину недоступности;
  он не угадывает состояние по PID/порту.
- П-4: `make test-ui` сначала обновляет собранный Caddy-образ, затем запускает
  Playwright; Vite на `:8477` даёт понятный отказ.
- П-5: `make up` остаётся единственным явным способом поднять полный собранный стенд.

## 8. Арбитр

- тест: `node --test tools/ops/dev-mode.test.mjs`, затем `make unit`;
- живой прогон: в одном терминале `make work`, изменить CSS и увидеть HMR; в другом
  `make dev-status` сообщает Vite. После остановки Vite — `make test-ui`, а
  `make dev-status` сообщает Caddy;
- сверка с источником: [Docker Compose Watch](https://docs.docker.com/compose/how-tos/file-watch/)
  подтверждает sync/HMR как dev-путь, [Docker Node development guide](https://docs.docker.com/guides/nodejs/develop/)
  разделяет dev и production, а [Caddy reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)
  подтверждает роль прокси.

## 9. Наблюдаемость

- проверяемый исход для человека: `make dev-status` печатает активный runtime и API-health;
- как может отказать и с каким кодом причины: недоступный `:8477`, неизвестный runtime,
  или недоступный API приводят к ненулевому коду и одному понятному сообщению;
- какие события пишем и какие поля в них безопасны: новые логи не нужны — диагностика
  локальная и не получает секреты;
- повтор / таймаут / идемпотентность / восстановление: GET-запросы безопасно повторяемы,
  короткий timeout; восстановление режима — `make up` для Caddy либо `make work` для Vite;
- чем докажем после выката: заголовок на реальном `:8477` и успешный UI-прогон Caddy.

## 10. Риски

- API-образ отсутствует после свежего клона → `make work` честно укажет запустить
  `make up` один раз; скрытую сборку обратно не добавляем.
- Vite и Caddy одновременно претендуют на `:8477` → `strictPort` и диагностика
  фиксируют конфликт; `test-ui` не продолжает на неправильном сервере.
- Новая диагностика станет вторым источником режима → она читает только заголовок,
  который устанавливают сами серверы; состояния в ней не хранятся.
- Docker Desktop недоступен среде → быстрые тесты всё равно проверяют рецепт;
  живой арбитр помечается блокированным, а не подменяется догадкой.
