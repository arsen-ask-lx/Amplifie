# task-123-ci-параллельно-без-потери-проверок: CI параллельно — те же проверки, в разы быстрее

Статус: в работе
Риск: средний
Заведено: 2026-09-27

## За 60 секунд

Тяжёлый этап CI — одна машина и одна очередь: стенд → цена запросов → приёмочные (2 мин) →
фаззер API (**45 мин**, 27.09) → k6 → браузерные. Каждый пуш отменяет прошлый прогон, поэтому
этап почти никогда не доходил до конца, и CI был красным неделями, а внутри никто не смотрел.
Режем его на параллельные машины GitHub, **не выкидывая ни одной проверки и не ослабляя ни
одной**: у каждой машины свой стенд, фаззер делится по дверям и фазам, браузерные — на
куски. Цель — тяжёлый этап до ~15 минут.

## 1. Зачем

Владелец 27.09: «ускорить до нормальных цифр, не теряя качества»; ноутбук не тянет полные
прогоны — их делает GitHub. Одобрен вариант А («ок го»), порядок шагов — «ок го».

## 3. Варианты

| Вариант | За | Против |
|---|---|---|
| **Параллельные работы, свой стенд у каждой; фаззер: фазы 1–3 по кускам дверей + `stateful` целиком; браузерные — `--shard` на 3** | те же проверки; падение видно своей работой; нет общей базы — нет мигания | +~2 мин подъёма стенда на работу → больше минут GitHub |
| Поднять темп фаззера | одна работа | меняет, что меряем: пороги частоты по человеку дают больше 429 — меньше настоящих примеров; без замера — догадка |
| Полный набор ночью, на пуш — часть | дёшево | ошибка живёт до ночи — владелец запретил жертвовать качеством |
| Собирать образы один раз и раздавать архивом | «собрал один раз» | `docker save/load` ~столько же, сколько сборка (68 с); лишний узел — KISS против |
| Кеш слоёв buildx в Actions (`cache-from/to: type=gha`) | подъём стенда быстрее у всех работ | правка сборки compose; решать по замеру подъёма в новых работах, не раньше |

Расхождения с решениями: нет. `workers: 1` в Playwright остаётся — параллель между машинами,
у каждой своя база, причина из комментария не нарушается.

## 4. Как делаем

1. Работа `stack` → четыре вида работ, все после быстрых не ждут (параллельно с ними):
   - `acceptance`: стенд → миграции → цена → приёмочные → k6 (одна база, всё короткое);
   - `api-fuzz` (матрица): `shard` 1..4 — `--phases examples,coverage,fuzzing` по своей
     четверти дверей; `stateful` — `--phases stateful` по всем;
   - `ui` (матрица 1..3): стенд → браузер → `test-ui -- --shard=N/3`;
   - `fail-fast: false` у матриц: упал один кусок — остальные досказывают.
2. Деление дверей — `tools/ops/fuzz-shards.mjs`: читает `backend/openapi.json`, выкидывает
   исключённые двери, делит **семьями** (производитель данных и потребитель — вместе:
   чаты с репликами, приглашения со входом, мост с кодами) на N кусков, ровняя по числу
   операций; порядок детерминирован. Тест: куски вместе дают все пути, и у каждой связи
   `links` оба конца в одном куске. Исключения с причинами — в одном месте, в модуле.
3. `api-fuzz.sh`: `FUZZ_SHARD=i/N` и `FUZZ_PHASES` — без них прогон как сейчас, целиком.
   Темп `300/m` не трогаем: сначала замер, почему он такой.
4. `concurrency: cancel-in-progress` остаётся: прогоны станут короткими, а пуш — пачками.
5. Следы при падении — у каждой работы свои (логи стенда, отчёт Playwright с номером куска).

## 5. Шаги

1. `fuzz-shards.mjs` + тест, `api-fuzz.sh` с кусками; локально — `make -n`, один малый кусок
   с `-n 5` по стенду.
2. `ci.yml`: работы и матрицы; `zizmor`, `actionlint` (через `make check`).
3. Пуш; замер времени работ и минут; разбор красного по новым работам — отдельно, по
   правилу «причина, а не следствие».
4. Ребаланс кусков по замеру, если один кусок заметно длиннее.
5. Журнал, карта, ревью.

## 6. Признаки приёмки — чем докажем

- П-1: набор проверок тот же — ни одной пропавшей двери и ни одной разрезанной связи (тест
  кусков); `stateful` — по всем 46 операциям; в каждой из трёх работ `ui` шаг проверок
  выполнен, а не пропущен.
- П-2: самая долгая тяжёлая работа ≤ 15 мин по времени GitHub (было 45+).
- П-3: минуты на прогон названы числом — владелец решает по ним про тариф.
- П-4: подсадки: потерянный путь → тест кусков красный; реплики отделены от чатов → тест
  связей красный.

## 7. Вопросы к тестам

- В-1: не теряется ли покрытие при делении фаззера?
  - почему важно: быстрый, но дырявый фаззер — ровно «жертвуем качеством».
  - как проверим: тест кусков (объединение = все пути); `stateful` — по всем операциям.
- В-2: не станет ли что-то мигать от параллели?
  - как проверим: у каждой работы своя машина и своя база; внутри Playwright — по-прежнему
    один поток.

## 11. Риски

- Минуты GitHub на приватном репозитории: ~12 работ на прогон вместо 4 → владелец смотрит
  остаток в настройках (у агента нет права `user`).
- Кусок фаззера окажется неровным → ребаланс по замеру (шаг 4).
- `stateful` целиком может оказаться сам по себе длинным → тогда его делить по связным
  группам дверей, не раньше замера.

## Разбор критика

Агент `plan-critic`, 27.09: «годен после правок; главная посылка неверна».

- (1) фазы 1–3 зависят между дверями — принято, сверено в образе; деление семьями, тест связей.
- (2) цель 15 мин без раскладки по фазам — принято частично: раскладки нет в логах (прогон
  не закончен), время каждой работы даст первый прогон; ребаланс — шаг 4. Отступление: владелец
  просил не ждать 45 минут.
- (3) условия от шага `cost` в новых работах — принято: в `api-fuzz` и `ui` условий нет,
  шаги по умолчанию не идут после упавшего подъёма.
- (4) нет `timeout-minutes` — принято: у каждой работы, около двойного замера.
- (5) минуты до пуша — принято: оценка ~80–90 мин на прогон против ~56; решает владелец по тарифу.
  `needs: quality` отвергнут: +1,5 мин к каждой обратной связи ради редкого красного линтера.
- (6) кеш buildx — принято в варианты; решать по замеру.
- (7) причины исключений в двух местах — принято: только в модуле.
- (8) ослабление двери в куске без неё — принято, проверено: кусок 3/4 без двери реплик идёт без ошибок;
  файл настроек общий, `stateful` получает ослабление.
- (9) одно имя отчёта у трёх `ui` — принято: имя с номером куска. Отчёт фаззера файлом — отвергнут:
  вывод в журнале работы уже содержит падения и команду повтора.
- (10) `Makefile` не нужен — принято, убран из границ.
- (11) П-4 = П-1, сумма спеков — принято: признаки переписаны.
- (12) устаревший комментарий про общий порог регистраций — принято: убран; файл настроек
  фаззера — свой на процесс.
- (13) `ui` на пустой базе — принято как риск: красное в первом прогоне разбирать как находку.

- Первые три фазы Schemathesis тоже берут данные у других дверей — деление «ровно по путям»
