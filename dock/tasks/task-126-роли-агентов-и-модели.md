## 3. Как делаем

1. **Роли — тонкие агенты.** `delegate-review` сейчас — команда
   (`.claude/commands/delegate-review.md`), а поле `skills:` подгружает только скиллы.
   Поэтому команда **переезжает** в `.claude/skills/delegate-review/SKILL.md` (`git mv`,
   одна копия; скилл вызывается тем же `/delegate-review` — документация скиллов: команды
   слиты со скиллами). Затем `.claude/agents/reviewer.md` (`model: sonnet`, только чтение
   и Bash, `skills: [delegate-review, test-quality]`), `researcher.md` (`model: sonnet`,
   чтение и веб, `skills: [research-before-build]`), `plan-critic.md` — `model: opus`,
   `skills: [plan-quality]`. Текст знания в агента не копируется.
2. **Таблица «этап → роль → модель»** — короткий раздел в `AGENTS.md` со ссылкой на
   справочник; скилл `delegate-review` называет агента `reviewer` и когда звать Opus.
   Сторож ревью (`isReviewer` в `tools/agent/trace-rules.mjs`) засчитывает только
   `subagent_type: "reviewer"` — как `isCritic` для критика; иначе новое поведение не
   отличить от старого (разбор критика).
3. **Сторож «CI красный — сначала разбор» — на коммите, а не на каждой правке.** Хук
   `commit-msg` (рядом с `review-audit`): последний законченный прогон CI ветки красный —
   берём имена упавших работ и тестов из `gh`; каждое упавшее есть в
   `tools/ratchets/ci-known-red.txt` со ссылкой на Д-NN — пропускаем; иначе коммит
   отклоняется до файла разбора `dock/ci/<прогон>.md` с четырьмя разделами (текст падения,
   класс, причина, что уже описано). Коммит редок и последователен — ни кеша, ни гонки
   параллельных агентов. Нет `gh` или сети — пропуск с предупреждением (fail-open назван
   вслух: иначе без сети нельзя закоммитить ничего).
4. **Скиллы:** `k6-load-testing` под наши `tools/load/k6/*.js` и `make k6*`;
   `security-review` — только раздел «fail-open» с примерами Fastify/Node.
5. **Усилие у ролей (дополнение владельца 27.09, до кода).** Официальный гайд Opus 5.5:
   effort — главный рычаг, по умолчанию `medium`, `xhigh`/`max` — только где прирост
   измерен. `plan-critic` — `effort: high`; `reviewer` — `effort: high`; `researcher` —
   `effort: medium`.
6. **Скилл по файлам — правилом с `paths:`, а не полем скилла (дополнение владельца
   27.09, до кода).** Сверено с документацией Claude Code: `paths:` у **скилла** только
   сужает самостоятельный выбор модели — скилл всё равно грузит модель, по описанию,
   и вне этих файлов он сам уже не подтянется (`test-quality` перестал бы грузиться при
   планировании тестов). `paths:` у **правила** `.claude/rules/*.md` — движок кладёт
   правило в контекст, когда прочитан подходящий файл, решает не модель
   ([память](https://code.claude.com/docs/en/memory#path-specific-rules),
   [скиллы](https://code.claude.com/docs/en/skills)). Поэтому короткие правила: «правишь
   такое — загрузи скилл X» и два-три главных пункта: миграции → `safe-migrations`;
   репозитории и запросы → `postgres-performance`; тесты → `test-quality`; Dockerfile и
   compose → скиллы Docker; поток и живые обновления → `centrifugo-realtime`; нагрузка →
   `k6-load-testing`. Сторож: у каждого правила пути находят хотя бы один файл в git,
   а названный скилл существует — иначе правило молча не сработает никогда.

### Варианты

| Вариант | За | Против |
|---|---|---|
| **Тонкие агенты поверх скиллов** | одна копия знания; свой контекст, модель, усилие, инструменты | три файла ролей |
| Всё скиллами (как `audit_project`) | одна копия, проще | теряем свой контекст ревьюера и модель по роли |

| Восьмиступенчатый конвейер `audit_project` | роли на каждый шаг | масштаб не наш; «простое надёжнее сложного» |

Расхождения с решениями: нет. Новых зависимостей нет (`gh` уже стоит).
