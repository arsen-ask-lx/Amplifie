# task-088-ряд-чисел-во-времени: Prometheus на стенде и агент, который читает метрики сам

Риск: низкий по коду (продукт не тронут), средний по оснастке: новый узел на стенде

## 1. Зачем

[task-087](task-087-числа-от-самого-сервера.md) научил сервер рассказывать
о себе числами, и они сразу сошлись со стендом до 0,0%. Но живут эти числа
**мгновением**: перезапуск процесса обнуляет счётчики, а между двумя опросами
не видно ничего.

Ряд во времени нужен для трёх разных вещей, и ни одну не закрывает мгновенный
опрос:

1. **форма кривой**, а не точка. Утечку памяти видно только так: пила
   вверх-вниз — обычная сборка мусора, храповик ступеньками вверх — утечка;
2. **что было ВО ВРЕМЯ прогона**, а не после. Замер длится десятки секунд,
   и самое интересное в нём — середина;
3. **агент читает числа сам** — тот самый замкнутый цикл, а не пересказ
   человеком.

## 2. Что уже есть

- `/metrics` на api: восемь чисел плюс RED по дверям (task-087);
- `compose.dev.yml` — всё, чего не должно быть у клиента; коробка собирается
  из одного `compose.yml`;
- `tools/` — оснастка, которая в продукт не попадает (по своду);
- правило проекта про порты: **свои, не стандартные** — на общих уже был
  разбор несуществующей поломки из-за чужого следа.

## 3. Как делаем

**Prometheus одним контейнером и только на стенде.** Объявлен в
`compose.dev.yml`; в коробке клиента его нет и быть не должно — лишний узел
у заказчика это лишний режим отказа (закон Люссера). Кому нужен свой
Prometheus — у того он уже есть, и `/metrics` ему хватит.

**Версия закреплена** (`prom/prometheus:v3.6.0`): плавающий тег даёт два
разных образа из одного коммита — ровно то, за что записан [Д-36](../debt.md#d-36).

**Опрос раз в 5 секунд.** Наши замеры длятся десятки секунд: при минутном
опросе прогон уместился бы между двумя точками целиком.

**Порт 9477, а не 9090** — по правилу проекта.

**Агент читает метрики официальным MCP** — `prometheus-mcp-server` из
организации Prometheus, образ с закреплённой версией, стдио-транспорт,
смотрит на `http://prometheus:9090` внутри сети стенда.

⚠️ **Граница, которую нельзя стереть** (закон Гудхарта): метрики агент
**читает**, приговор выносят **гейты**. Дай агенту метрику и право её
улучшать — он начнёт улучшать метрику, а не продукт.

## 4. Чем докажем

- **П-1.** `up{job="amplifie"} == 1` — Prometheus видит цель;
- **П-2 — главный.** Прирост счётчика **по ряду** за отрезок совпадает
  с приростом того же счётчика **по прямому опросу** за тот же отрезок:
  расхождение не больше 5%;
- **П-3.** Ряд переживает перезапуск процесса: после перезапуска api
  в окне видно **обнуление счётчика** и не меньше 10 точек;
- **П-4.** Клиенту Prometheus не достаётся: `docker compose -f compose.yml
  config` упоминает его **0 раз**;
- **П-5.** Образ MCP запускается и видит Prometheus: в журнале — версия,
  адрес и число инструментов.

## 5. Границы

- **трогаем:** `compose.dev.yml`, новый `tools/ops/prometheus.yml`, `.mcp.json`,
  документы;
- **не трогаем:** продукт — ни строки; `compose.yml` — коробка остаётся
  прежней; Caddyfile — `/metrics` остаётся внутренней дверью.

## 6. Риски

- **Лишний узел на стенде.** Он не в коробке, но он есть у нас: ещё один
  контейнер, который надо поднимать. Смягчено тем, что стенд и так
  из четырёх частей, а этот узел ничего не обслуживает — только читает;
- **Метрика как цель.** См. границу выше;
- **MCP проверен не до конца.** Образ запускается и видит Prometheus —
  это проверено. А что Claude Code с ним заговорит, проверится только
  после перезапуска сессии: настройки читаются на старте.
