# task-001-мост-участника: каждый подключает свою подписку через мост на своей машине

Статус: одобрен (словами, 2026-09-06)
Риск: высокий
Заведено: 2026-09-06

---

## 1. Зачем

Светлана и Пётр работают в одном пространстве. У каждого своя подписка Claude.
Сегодня спросить модель из продукта не может ни один из них: провайдер
в коде есть, но сервер живёт в контейнере, где клиента `claude` нет и учётных
данных нет тоже. Проверено: `docker compose exec api which claude` — пусто.

После задачи, **со стороны человека**: Пётр заходит на сайт, открывает
«Подключить свою нейросеть» и видит две плитки.

- **Ключ API** — вставил ключ, нажал «проверить», готово. Целиком на сайте;
- **Подписка Claude** — сайт показывает готовую строку с уже вписанным кодом
  подключения и словами «скопируйте и выполните у себя один раз». Пётр
  копирует, вставляет в свой терминал — и страница **сама**, без обновления,
  меняется на «ваша подписка: на связи».

Инструкция, код и состояние живут на сайте. У себя человек делает одно
действие один раз.

**Почему подписку нельзя, как ключ, просто вставить в поле.** Ключ — это
строка, её можно отдать нам, и дальше спрашивает наш сервер. У подписки такой
строки нет: она привязана к входу в клиент на конкретной машине. Вставлять
нечего; а если бы было — это был бы токен подписки, то есть ровно то,
что запрещено ([Р-012](../decisions.md#r-012)) и что вернуло
бы всех на одну машину под одним аккаунтом.

С этого момента вопросы Петра к модели уходят через **его** подписку,
а вопросы Светланы — через её. Токен подписки не покидает их машин:
мы его не видим и не храним.

Почему иначе нельзя: Anthropic запретил подписочную OAuth-аутентификацию
для сторонних продуктов ([Р-012](../decisions.md#r-012)).
Единственная законная форма — запрос делает **его** официальный клиент
на **его** машине.

## 2. Что уже есть

- `apps/api/src/agent/model/provider.ts` — интерфейс «спросить текстом»,
  типы ошибок `ProviderUnavailableError` / `BadAnswerError`;
- `apps/api/src/agent/model/cli.ts` — запуск официального клиента через
  `spawn`, подсказка в стандартный ввод, таймаут, потолок вывода.
  **Переиспользуется мостом как есть** — переносится в общий код;
- `apps/api/src/agent/model/choose.ts` — выбор провайдера по настройкам;
- `scripts/check-model.mjs` + `make model` — живая диагностика: спрашивает
  настоящую модель, а не смотрит на настройки;
- `kernel/identity` — участники и сессии; `Р-009` — рабочий образец
  одноразового токена: 256 бит, хеш в базе, погашение условным `UPDATE`;
- `platform/bus.ts` — звонок по SSE (для этой задачи не нужен, см. §3).

С нуля пишется только сам мост и его две ручки.

## 3. Как делаем

**Соединение открывает машина человека, а не сервер.** У ноутбука нет
открытого адреса, к нему нельзя подключиться снаружи. Поэтому мост сам
приходит за работой: держит запрос `GET /v1/bridge/next` до 25 секунд
(«длинное ожидание»: сервер не отвечает, пока не появится задание или
не выйдет срок), получает задание, запускает у себя `claude`, возвращает
ответ через `POST /v1/bridge/answer`. Так устроены раннеры CI.

**Очереди в базе не заводим.** Задание живёт в памяти процесса: запрос
«спроси модель» ждёт ответа моста и отдаёт его тем же ответом HTTP.
Перезапуск сервера теряет незавершённые вопросы — это приемлемо: вопрос
задаётся заново, ничего не испорчено.

Почему не WebSocket: длинное ожидание решает ту же задачу обычным HTTP,
проходит через тот же Caddy и не заводит второй транспорт.

**Расхождения с принятыми решениями:**

1. **`AGENTS.md` §«Чего в этом проекте нет» утверждает: «нет очереди
   и фоновых работ — всё синхронно внутри запроса».** Здесь появляется
   ожидание в памяти между двумя запросами. Формально это не очередь
   (ничего не хранится, ничего не переживает перезапуск), но фраза
   в своде правил становится неточной и её надо поправить. **Вопрос
   человеку, а не самовольная правка.**
2. **[Р-012](../decisions.md#r-012) описывает подписку как
   «наш сервер запускает официальный клиент».** Фактически сервер в контейнере
   и запустить не может. Предлагается уточнение: клиент запускает мост
   на машине владельца подписки. Суть решения — «токен не покидает своего
   клиента» — сохраняется полностью. **Требуется правка Р-012 отдельным
   набором, после одобрения этого плана.**

## 4. Шаги

1. **Общий код запуска клиента.** `cli.ts` переезжает туда, откуда его
   видят и сервер, и мост. Поведение не меняется.
   - файлы: `apps/api/src/agent/model/cli.ts` → `packages/model-cli/`
   - проверка: `make typecheck`, существующие 9 быстрых тестов зелёные

2. **Хранилище мостов.** Таблица `bridge`: участник, имя машины, хеш токена,
   последний контакт. Плюс одноразовый код подключения по образцу Р-009.
   - файлы: `kernel/identity/schema.ts`, новая миграция
   - проверка: миграция применяется на чистой базе и на текущей

3. **Ручки моста.** `POST /v1/bridge/join` (код → постоянный токен),
   `GET /v1/bridge/next` (длинное ожидание), `POST /v1/bridge/answer`.
   Токен моста — не сессия браузера: отдельная проверка, отдельный тип.
   - файлы: `surface/http/routes/bridge.ts`, `app/bridging.ts`
   - проверка: приёмочные В-2, В-3, В-4

4. **Провайдер «мост».** Спрашивает модель через мост конкретного участника;
   мост не на связи — `ProviderUnavailableError` с внятной причиной.
   - файлы: `agent/model/bridge.ts`, `choose.ts`
   - проверка: приёмочный В-5

5. **Сама программа моста.** Код подключения из аргумента, цикл ожидания,
   запуск клиента, ответ. Повторное соединение при обрыве. `make bridge`.
   - файлы: `apps/bridge/`, `Makefile`, `.env.example`
   - проверка: живой прогон

6. **Экран «Подключить свою нейросеть».** Кнопка выдаёт код один раз и сразу
   показывает готовую к копированию строку запуска. Ниже — состояние:
   «на связи» / «нет связи» и время последнего контакта, обновляется само.
   Экран рассчитан на две плитки; вторая — ключ API — приезжает следующей
   задачей и встаёт сюда же, без переделки.
   - файлы: `apps/web/src/BridgePanel.tsx`, `api.ts`, `styles.css`
   - проверка: `make contrast`, живой прогон

7. **Наблюдаемость и диагностика.** Контур `bridge.job.*`; `make model`
   умеет спрашивать через мост и говорит словами, что не так.
   - файлы: `platform/log.ts`, `scripts/check-model.mjs`
   - проверка: живой прогон, чтение логов

## 5. Признаки приёмки

- **П-1:** запускаю `make bridge КОД=<код>` на своей машине → в профиле
  на сайте появляется строка «<имя машины> · на связи».
- **П-2:** нажимаю «проверить» → в течение 30 секунд вижу ответ настоящей
  модели на контрольный вопрос, и это ответ по существу вопроса.
- **П-3:** закрываю терминал с мостом → не позже чем через минуту в профиле
  «нет связи»; попытка спросить модель даёт сообщение «мост не на связи»,
  а не пятисотку и не молчание.
- **П-4:** код подключения, выданный в чужом пространстве, не даёт доступа
  к моему: ответ 404, неотличимый от «такого кода нет».
- **П-5:** код подключения срабатывает **один раз**; вторая попытка тем же
  кодом отклоняется, даже если обе пришли одновременно.
- **П-6:** в логах есть `bridge.job.успех` с длительностью, и в них нет
  ни текста вопроса, ни текста ответа, ни токена.

## 6. Вопросы к тестам

- **В-1:** «Одноразовый код подключения действительно одноразовый под гонкой?»
  - почему важно: код даёт постоянный доступ от имени участника. Два моста
    по одному коду — это чужая машина, отвечающая за человека;
  - как проверим: два одновременных `join` одним кодом → ровно один успех.
    Приём уже проверен на приглашениях, но там другая таблица и другой запрос;
  - тестов: 1–2

- **В-2:** «Ждущий вопрос получает ответ именно своего моста?»
  - почему важно: два участника спрашивают одновременно; перепутанные ответы
    означают, что человек увидел чужой текст;
  - как проверим: два поддельных моста, два вопроса, сверка попарно;
  - тестов: 1–2

- **В-3:** «Что происходит, когда мост молчит?»
  - почему важно: молчание — обычное состояние (ноутбук уснул). Оно обязано
    заканчиваться внятной ошибкой, а не висящим запросом;
  - как проверим: вопрос без подключённого моста → ошибка «не на связи»
    за предсказуемое время; вопрос при мосте, который взял задание
    и не ответил, → срок вышел, ошибка;
  - тестов: 2

- **В-4:** «Токен моста не пускает туда, куда пускает сессия, и наоборот?»
  - почему важно: это разные удостоверения с разными правами. Слитые вместе,
    они дают машине права человека в интерфейсе;
  - как проверим: токеном моста в `/v1/me` → 401; сессией в `/v1/bridge/next`
    → 401;
  - тестов: 2

- **В-5:** «Ответ моста не считается доверенным?»
  - почему важно: мост присылает текст, порождённый моделью, а модель читала
    ленту. Это недоверенный ввод по определению;
  - как проверим: ответ с разметкой и служебными последовательностями
    доезжает как текст и не исполняется на клиенте (гейт `no-raw-html`
    это стережёт, тест закрепляет);
  - тестов: 1

**Бюджет:** ожидаю 400–500 изменённых строк, отсюда 8–10 тестов. Вышло
заметно больше — значит проверяю реализацию, а не задачу.

## 8. Арбитр

- **тест:** `bridge.e2e.test.ts` на живом стеке с **поддельным мостом**
  (обычный HTTP-клиент в тесте, изображающий мост). Доказывает: гонку кода,
  адресацию ответов, поведение при молчании, разделение удостоверений;
- **живой прогон:** запускаю настоящий мост на своей машине с настоящей
  подпиской, спрашиваю через сайт, получаю ответ. Затем гашу мост
  и убеждаюсь, что сайт говорит «нет связи», а не висит;
- **логи обеих сторон:** контур `bridge.job.*` записан на сервере, мост
  напечатал у себя начало и исход. Секретов ни там, ни там.

Поддельный мост в тесте **не заменяет** живого прогона: подделка структурно
слепа на швах — установка клиента, вход в него, сеть, контейнер.

## 9. Наблюдаемость

- **проверяемый исход для человека:** в профиле видно состояние моста
  и время последнего контакта; кнопка «проверить» отвечает словами;
- **как может отказать:** мост не подключён · подключён, но не отвечает ·
  клиент не установлен · вход в клиент истёк · клиент вернул пусто.
  Пять разных причин, пять разных сообщений — «что-то пошло не так»
  здесь бесполезно, потому что чинит их человек и по-разному;
- **события:** `bridge.job.начало` / `.успех` / `.отказ` с длительностью,
  идентификатором участника и класcом ошибки. **В полях — опознаватели,
  а не значения:** ни вопроса, ни ответа, ни токена, ни имени машины
  дальше строки состояния;
- **повтор:** мост, взявший задание и упавший, не оставляет его висеть —
  срок ожидания истекает, вопрос отвечает ошибкой. Повторный вопрос
  человек задаёт сам: молча повторять запрос к платной модели нельзя;
- **чем докажем после выката:** `make model` через мост отвечает, и в логе
  есть пара «начало / успех» с разумной длительностью.

## 10. Риски

- **токен подписки утечёт через нас** → не может: мы его не видим. Мост
  запускает клиент, клиент читает свои учётные данные сам. Проверить, что
  в логах моста нет содержимого `~/.claude`;
- **мост исполняет то, что пришло с сервера** → сервер присылает только
  текст вопроса; команда запуска берётся из настроек **на машине человека**
  и никогда из ответа сервера. Это то же правило, что в `cli.ts`, и его надо
  повторить в мосте явно;
- **закрыл терминал — тишина** → видимое состояние и внятная ошибка (П-3).
  Порог для установки службы в систему: человек, который забывает запускать
  мост чаще раза в неделю;
- **два процесса сервера** → ожидание в памяти перестанет работать: вопрос
  придёт в один процесс, а мост будет ждать в другом. Порог для настоящей
  очереди — второй процесс. Записать это в `AGENTS.md` вместе с правкой
  про «нет очереди»;
- **чужой мост отвечает за человека** → одноразовый код и отдельный тип
  токена (В-1, В-4);
- **цена вопроса** → каждый вопрос тратит подписку человека. Счётчика
  расхода подписка не даёт; в журнале будет только число вопросов
  и длительность.
