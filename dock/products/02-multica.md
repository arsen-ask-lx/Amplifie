# Multica — разбор

> Разобран по исходникам 2026-09-04. Локально: `/e/other_project_for_example/multica`.
> Продукт **не поднимался**, только чтение кода.

**Одной фразой:** доска задач, на которой агенту поручают работу так же, как товарищу
по команде: он берёт задачу, докладывает о ходе, поднимает препятствия и сдаёт на приёмку.

| | |
|---|---|
| Звёзд | ~48 000 в `repos.txt`, ~37 000 по обзору (расхождение ⚠️) |
| Язык | Go (сервер) + TypeScript (клиенты) |
| Лицензия | ⛔ **«Multica License»** = Apache-2.0 + запрет коммерческого размещения. Разбор в §8 — **это дисквалифицирует multica как основу** |
| Размер | 5 375 файлов · **132 таблицы** · 936 файлов миграций |
| Состав | `server` (Go) + `apps/web`, `apps/desktop`, `apps/mobile`, `apps/docs` + `packages/*` |
| Зрелость | v0.2.x — раннее ПО |

## 1. Разделы

Боковая панель, три группы, 12 пунктов:

| Группа | Пункты |
|---|---|
| **Личное** | Inbox · Chat · My Issues |
| **Пространство** | Issues · Projects · **Autopilots** · **Agents** · **Squads** · Usage |
| **Настройка** | **Runtimes** · **Skills** · Settings |

Разделы в коде (`packages/views`): agents, autopilots, chat, dashboard, editor, inbox,
invitations, issues, labels, members, my-issues, onboarding, projects, runtimes, search,
settings, skills, squads, workspace + интеграции: slack, telegram, lark, dingtalk, wecom.

## 2. Модель данных — 132 таблицы

Крупные группы: `issue*` (12), `plugin_*` (20), `channel_*` (12), `autopilot_*` (8),
`task_usage_*` (10 — учёт расхода с почасовой и посуточной свёрткой), `lark_*` (7),
`agent*` (7), `github_*`/`vcs_*` (8), `skill*` (3), `squad*` (2), `chat_*` (4).

### Задача — 17 столбцов, вдвое проще, чем у paperclip

```sql
assignee_type TEXT CHECK (assignee_type IN ('member','agent'))
assignee_id   UUID
creator_type  TEXT NOT NULL CHECK (creator_type IN ('member','agent'))
creator_id    UUID NOT NULL
acceptance_criteria JSONB NOT NULL DEFAULT '[]'
context_refs        JSONB NOT NULL DEFAULT '[]'
```

Три вещи заметны:

1. **Полиморфный участник** (`assignee_type` + `assignee_id`) — прямо противоположный
   выбор по сравнению с paperclip, где два раздельных столбца. Это настоящая развилка,
   с которой мы столкнёмся, и вот два живых образца обоих решений.
2. **`acceptance_criteria` прямо в задаче** — приёмочные критерии как поле, а не как проза
   в описании. Это ровно «арбитр» из вашей же стратегии, доведённый до модели данных.
3. **`context_refs`** — ссылки на контекст задачи отдельным полем.

Статусы: `backlog · todo · in_progress · in_review · done · blocked · cancelled`.

### Агент — 12 столбцов, гораздо проще paperclip

```sql
runtime_mode TEXT CHECK (runtime_mode IN ('local','cloud'))
visibility   TEXT DEFAULT 'workspace' CHECK (visibility IN ('workspace','private'))
status       TEXT CHECK (status IN ('idle','working','blocked','error','offline'))
max_concurrent_tasks INT NOT NULL DEFAULT 1
owner_id     UUID REFERENCES "user"(id)
```

Иерархии `reportsTo`, как у paperclip, нет — вместо неё **отряды** (`squad`, `squad_member`).
У агента есть владелец-человек и признак приватности.

### Чат — это разговор с агентом, а не между людьми

```sql
CREATE TABLE chat_message (
    chat_session_id UUID NOT NULL,
    role TEXT NOT NULL CHECK (role IN ('user', 'assistant')),
    content TEXT NOT NULL,
    task_id UUID
);
```

`role IN ('user','assistant')` — классическая переписка с моделью. **Автора-человека тут нет
как поля.** Значит «Chat» в сайдбаре — это консоль агента, а не канал команды.
Люди говорят друг с другом только в комментариях к задачам.

### Навык = папка файлов

```sql
skill(name, description, content, config) + skill_file(path, content) + agent_skill(M:N)
```

То же устройство, что у навыков Claude Code: описание + тело + приложенные файлы.
Отсюда «складывающиеся навыки» из обзоров: решённая задача сохраняется как
переиспользуемое умение.

## 3. Откуда берётся работа

**Автопилоты** — три вида запуска, и ни одного «по сообщению»:

```sql
autopilot_trigger.kind CHECK (kind IN ('schedule', 'webhook', 'api'))
autopilot_run.source   CHECK (source IN ('schedule','manual','webhook','api'))
```

**Внешние чаты** — Slack, Telegram, Lark/Feishu, DingTalk, WeCom. И тут прямая цитата
из их документации, важная для нас:

> «Сообщения в канале, которые **не упоминают бота, никогда не запускают агента** и не
> добавляются в его контекст разговора.»

Задача заводится командой `/issue`. На Slack — «агент пишет описание перед созданием»,
на остальных площадках — «создаёт задачу из вашего текста как есть».

Управление разговором: `/new` (новый разговор), `/clear` (оставить разговор, но обрезать
видимый агенту контекст).

**Механика приёма входящих сообщений** — сделана аккуратно:

```sql
channel_inbound_message_dedup(installation_id, message_id) PRIMARY KEY + claim_token
channel_inbound_audit
channel_task_delivery(..., route_revision BIGINT)
```

Ровно-однократная обработка входящего: составной ключ + токен захвата. Плюс отдельный
аудит входящего и версия маршрута доставки.

### Контекст задачи из обсуждения — `issue_source_context`

Самое близкое к нашему К5:

```sql
source_issue_id     UUID NOT NULL   -- из какого обсуждения
anchor_comment_id   UUID NOT NULL   -- от какого комментария
snapshot            JSONB NOT NULL  -- слепок обсуждения
capture_digest      TEXT NOT NULL   -- отпечаток слепка
state TEXT CHECK (state IN ('pending','attached','abandoned'))
```

С жёстким инвариантом прямо в таблице:

```sql
CHECK (
  (state='pending'   AND issue_id IS NULL     AND origin_task_id IS NOT NULL AND attached_at IS NULL)
  OR (state='attached'  AND issue_id IS NOT NULL AND attached_at IS NOT NULL)
  OR (state='abandoned' AND issue_id IS NULL     AND attached_at IS NULL)
)
```

Жизненный цикл: захватили слепок → агент создаёт задачу → слепок прикрепился, либо
брошен. Невозможные сочетания запрещены базой, а не кодом.

## 4. Лучшее, что есть в multica: модель ответственности

`server/internal/attribution/attribution.go`. Разделены **два разных человека**:

| Понятие | Что значит | На что влияет |
|---|---|---|
| **originator** (`UserID`) | чьей властью действует агент | **разрешения** |
| **accountable** (`AccountableUserID`) | кто отвечает за результат | **аудит и отчётность** |

Восемь источников ответственности:

```
direct_human · delegation · comment_source · trigger_owner · rule_owner
owner_fallback · backfill · unattributed
```

И метод `Source.Precise() bool` — точный источник или выродившийся.

Три правила, которые стоит списать дословно:

1. **Цепочка ответственности переживает глубину.** Агент запустил агента запустил агента —
   `ParentAccountable` копируется вниз, «чтобы корень цепочки оставался стабильным на любой
   глубине». При этом `originator` остаётся `NULL`, то есть **разрешения не наследуются вниз**.
2. **Выродившаяся привязка помечена, а не спрятана.** `OwnerFallback` делает владельца агента
   ответственным, когда точного человека нет, но это «**УХУДШЕННАЯ** метка, и она обязана
   показываться отдельно в отчётности». В комментарии прямым текстом: «человек никогда
   не выдумывается».
3. **Режим fail-closed.** Пространство может потребовать точной привязки: если ответственного
   человека определить не удалось — **запуск отклоняется** (`attribution_blocked`).

## 5. Каталог отказов — образец инженерной культуры

`server/internal/dispatch/reason.go`. Отдельный пакет-лист (без внутренних зависимостей),
чтобы слой сервиса и слой обработчика **не могли разойтись** в трактовке.

Из шапки файла, дословно по смыслу: код причины решается в той ветке, которая блокирует
запуск, и доносится до ответа дословно; он **никогда не восстанавливается обратно из
человекочитаемой строки ошибки**. Коды стабильны, локализуемы клиентом и
**безопасны к перебору**: код никогда не выдаёт, существует ли приватный агент,
как он называется и чей он.

Успех: `queued` · `coalesced` · `deferred`.
Отказы: `invocation_not_allowed` · `target_unavailable` · `runtime_offline` ·
`runtime_unusable` · `agent_runtime_required` · `attribution_blocked` · `already_active` ·
`self_trigger_suppressed` · `quota_exceeded` · `issue_limit_reached` · `internal_error`.

Каждый код снабжён комментарием, **почему он отличается от соседнего**, со ссылкой на
конкретный инцидент. Например, зачем `runtime_offline` отделён от `agent_runtime_required`:
«клиенты, которые их схлопывают, отправляют пользователя искать выключенный компьютер,
которого не существует».

**`self_trigger_suppressed`** — защита от самозапуска: собственный комментарий агента
(или упоминание отрядом самого себя) не заводит новый прогон.

## 6. Плюсы и минусы

### Плюсы

- **Модель ответственности** — самая продуманная из трёх продуктов; готовый ответ
  на развилку «агент — роль или инструмент»;
- **каталог причин отказа** — образец, как делать вокабуляр ошибок;
- **приёмочные критерии полем в задаче**;
- **ровно-однократная обработка входящих** сообщений из внешних чатов;
- инварианты состояния выражены `CHECK`-ами в базе, а не соглашениями в коде;
- ~26 агентских CLI без привязки к одному поставщику (Claude, Codex, Hermes, OpenClaw,
  Gemini, Pi, Cursor — на одной доске, из одной библиотеки навыков);
- шесть чат-площадок из коробки, включая Telegram — это прямо ваш вопрос В-3;
- три клиента: веб, настольный, мобильный.

### Минусы

- ⛔ **Лицензия запрещает то, ради чего вы строите Amplifie** — подробно в §8;
- **Go на сервере** — не ваш язык; из бизнес-ТЗ у вас TypeScript;
- **чат — консоль агента, а не канал команды** (`role: user|assistant`);
- **агент не слушает**: только `@упоминание` и команда `/issue`; автопилоты запускаются
  расписанием, вебхуком или вызовом API;
- по обсуждению [#815](https://github.com/multica-ai/multica/issues/815):
  «Multica всё ещё управляет ИИ так же, как людьми» — запуск по назначению задачи сделан
  **зашитым промптом по умолчанию**, а не настраиваемым движком процессов; это «не ядро
  оркестрации, а шаблон исполнения по умолчанию»;
- v0.2.x, «ожидайте шероховатостей»;
- часть площадок (DingTalk, WeCom, Telegram) — на поддержке сообщества, без обязательств;
  WeCom и Telegram понимают только текст.

## 7. Что берём себе

| Приём | Зачем нам |
|---|---|
| **Разделение originator / accountable** | разрешения и ответственность — разные вопросы; это ответ на В-4 |
| **`Source.Precise()` и помеченная выродившаяся привязка** | «человек никогда не выдумывается» |
| **Режим fail-closed по ответственности** | нет ответственного — агент не запускается |
| **`ParentAccountable` вниз по цепочке, `originator` — нет** | глубина не размывает ответственность и не наследует права |
| **Каталог кодов отказа в отдельном пакете-листе** | слои не разойдутся; коды не выдают существование приватных объектов |
| **`self_trigger_suppressed`** | слушающий агент не должен реагировать на самого себя — иначе вечный цикл |
| **`acceptance_criteria` полем задачи** | арбитр в модели данных, а не в прозе |
| **`issue_source_context` со слепком и `capture_digest`** | наш К5: задача несёт слепок обсуждения, из которого выросла |
| **Инварианты состояния через `CHECK`** | невозможные сочетания запрещены базой |
| **Дедупликация входящих `(installation_id, message_id)` + `claim_token`** | ровно-однократная обработка сообщения |
| **`/new` и `/clear` для контекста** | человек управляет тем, что агент помнит |

### Чего НЕ брать

- 20 таблиц плагинов и 10 таблиц учёта расхода со свёртками — это масштаб облачного
  сервиса, не первого среза;
- 7 таблиц под одну площадку (Lark) — интеграции делать по одной и по надобности;
- зашитый промпт как «движок процессов» — их же сообщество называет это ошибкой.

## 8. ⛔ Лицензия — разбор, и почему это отсекает multica как основу

GitHub показывал `NOASSERTION`, потому что лицензия нестандартная. Файл `LICENSE`
прочитан целиком 2026-09-04. Это **Apache-2.0 плюс дополнительные условия**, и они
меняют всё:

> «Если вы не получили коммерческую лицензию от производителя, вы **не вправе**
> использовать исходный код Multica, чтобы предоставлять размещённый сервис третьим
> лицам, либо встраивать Multica как составную часть продукта или сервиса, который
> продаётся, лицензируется или иным образом коммерчески распространяется третьим лицам.»

И, чтобы не осталось лазейки, там же:

> «Предоставление размещённого сервиса третьим лицам ограничено **независимо от того,
> берёте ли вы плату**. Публично доступный экземпляр, работающий для пользователей
> **за пределами вашей собственной организации**, требует коммерческой лицензии, даже
> если предлагается бесплатно, не несёт рекламы и не продаёт платных тарифов.»

Что это значит по пунктам:

| Что вы делаете | Можно? |
|---|---|
| Пользуетесь внутри **своей** компании, хоть в нескольких пространствах | ✅ да |
| Форкнули и опубликовали исходники форка | ✅ да, но это **не даёт права запускать сервис** |
| Подняли экземпляр для людей вне вашей организации, бесплатно | ⛔ нужна коммерческая лицензия |
| Встроили в Amplifie и продаёте | ⛔ нужна коммерческая лицензия |
| Убрали логотип и название Multica из интерфейса | ⛔ нужен отдельный письменный отказ от условия |

Условие (b) отдельно оговаривает, что «интерфейсом Multica» считается всё, что
происходит из `apps/web/`, `apps/desktop/`, `apps/mobile/`, `packages/views/`,
`packages/ui/` — **включая переименованный, перемещённый или вынесенный в другой
репозиторий код**. Условие (c): даже если брать только `server/`, демон или CLI
без их интерфейса — обязаны сохранить все уведомления и написать в документации,
что продукт построен на Multica, со ссылкой.

Условие (d): отказ от брендирования — **не** коммерческая лицензия, и наоборот;
каждое разрешение надо получать отдельно и явно.

**Вывод.** Amplifie по замыслу — это размещённое рабочее пространство для компаний,
то есть ровно тот случай, который запрещён. **Multica отпадает как основа для форка
или встраивания.** Остаётся как источник идей: читать код, перенимать приёмы (§7)
и писать своё — это лицензия не ограничивает.

⚠️ Я не юрист; вывод сделан по тексту лицензии. Если основа на multica всё же
рассматривается всерьёз — это вопрос к юристу и/или письмо производителю за
коммерческой лицензией.
