# Р-015. TypeScript 6.0.3, а не 7.0.2

| | |
|---|---|
| **Статус** | ✅ принято 2026-09-07 |
| **Связано** | [Р-001](001-язык-и-рантайм.md) · [Р-003](003-оснастка-качества.md) |

| **План** | [task-005](../tasks/task-005-актуальные-версии.md) |
| **Пересмотреть** | когда выйдет TypeScript 7.1 с опубликованным compiler API |

## Что произошло

Владелец просил самые свежие стабильные версии. Последняя стабильная —
**7.0.2**. Поставили. Проверки формально прошли: типы зелёные,
`noUncheckedIndexedAccess` ловится, ошибок ноль.

А потом гейт границ модулей напечатал:

```
✔ no dependency violations found (0 modules, 0 dependencies cruised)
```

**Ноль модулей.** Подсаженное нарушение `kernel` → `surface` он не увидел
и вернул код 0. dependency-cruiser сам объяснил причину:

> dependency-cruiser detected a TypeScript environment, but not a compatible
> TypeScript compiler (typescript: >=2.0.0 <7.0.0). Support for typescript@>=7
> will follow when its API is published and stable.

TypeScript 7 — это перенос компилятора на Go, и его **compiler API появится
только в 7.1**. Всё, что импортирует компилятор как библиотеку, седьмую версию
пока не понимает. dependency-cruiser — ровно этот случай.

## Решение

**Берём 6.0.3.** На ней гейт видит 65 модулей и 127 связей и краснеет на
подсадке.

Довод одной строкой: **актуальная версия, которая гасит сторожа, актуальной
для нас не является.** Мы бы получили не «свежий компилятор», а молчащий
арбитр границ — и узнали бы об этом в тот день, когда кто-то нарушит границу.

Шестёрка — не «старьё»: это текущая поддерживаемая ветка, и именно с неё
все руководства советуют идти на семёрку, потому что она показывает
ломающие изменения предупреждениями.

**Что для этого пришлось сделать в коде:** ничего. Ломается конфигурация
(убраны `--baseUrl`, `--target es5`, `--moduleResolution node10`), а у нас
ни одного из них не было.

## Сторож этого решения

Добавлен `tools/checks/check-arch.mjs` — обёртка, которая роняет сборку,
если обход прошёл меньше чем по 20 модулям **или** если инструмент сам
сообщил, что мог что-то пропустить.

Проверено настоящей подсадкой: с 7.0.2 гейт краснеет с внятным текстом,
с 6.0.3 — зелёный и видит 65 модулей. То есть если кто-то поднимет версию
не подумав, он узнает об этом сразу, а не через месяц.

Это уже второй случай за день, когда проверка возвращает зелёный при нуле
проделанной работы (первый — `run-gates.mjs` после переезда каталога).
Складывается в правило: **у сканирующей проверки числа важнее вердикта.**

## Заодно: почему тесты не считаются в повторах

Запись `duplicate-code` при установке нашла 18 повторов: 13 в приёмочных
тестах, 5 в прод-коде.

Тестовые повторы — подготовка сценария: зарегистрировать, войти, создать
пространство. Вынести её в общий помощник значит связать тесты друг с другом
и сделать упавший тест нечитаемым: причину придётся искать во втором файле.
Это давно названная развилка — тесты пишутся **понятными, а не сухими**.

Поэтому `tools/checks/check-duplicates.mjs` смотрит только прод-код, а пять
найденных повторов записаны в храповик `tools/ratchets/duplicate-code.txt`:
число может уменьшаться, любой новый повтор красит сборку. Проверено
подсадкой шестого.

## Что это стоит

- мы **не получаем** 8–12-кратного ускорения полной сборки, которое даёт
  седьмая версия. Наша сборка идёт секунды, цена приемлемая;
- вернуться к вопросу придётся: строка стоит в очереди работ, а условие
  названо сверху — выход 7.1 с compiler API;
- пять повторов в прод-коде остаются долгом. Они перечислены поимённо
  в реестре, а не растворены в «когда-нибудь почистим».
