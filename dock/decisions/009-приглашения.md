# Р-009. Приглашения

| | |
|---|---|
| **Статус** | ✅ принято 2026-09-06 |
| **Почему сейчас** | права доступа — прямой триггер правила «сначала ресёрч»; переделать потом = переписать выданные ссылки |
| **Связано** | [Р-003](003-оснастка-качества.md) · [.temper/rules/security.md](../../.temper/rules/security.md) |

## Решение

**Ссылка-приглашение с одноразовым токеном.** Почты мы не шлём — значит
ссылку владелец передаёт сам, любым способом.

| Свойство | Значение | Почему так |
|---|---|---|
| длина | **256 бит** случайности, base64url | отрасль требует минимум 128; берём вдвое, стоит это ноль |
| хранение | **только SHA-256 от токена** | токен — это пароль. Утечка дампа не должна давать входа |
| срок | **7 дней** | не 15 минут: это не письмо для сброса пароля, ссылку передают руками |
| использование | **однократное**, гасится атомарно | два устройства одновременно → войдёт один |
| отзыв | есть, в любой момент | выдал не тому — закрыл, не дожидаясь срока |
| ответ на плохой токен | **404 и ничего больше** | иначе по ответу перебирают живые приглашения |

## Класс уязвимости, ради которого это решение и написано

У чужого продукта нашли и опубликовали такое: **тот же токен приглашения,
поданный через ДРУГОЙ поток входа, обходил проверку доступа**. Ошибка не в
токене — в том, что путей входа оказалось два, и второй забыли проверить.

Отсюда жёсткое правило: **вход по приглашению — ровно один путь**,
`POST /v1/auth/join`. Регистрация (`/v1/auth/register`) приглашений
не принимает **никогда** и продолжает делать только своё: новый аккаунт
со своим новым пространством. Никакого «а если передали токен —
присоединим».

## Что обязано выполняться всегда

Список взят из разбора чужих ошибок и переписан в приёмочные проверки:

1. токен предъявлен **дважды** — второй раз отказ, второго участника нет;
2. токен предъявлен **после срока** — отказ;
3. токен **отозван** — отказ;
4. токен предъявлен **с двух устройств одновременно** — ровно один входит;
5. **несуществующий токен** и **чужой токен** дают один и тот же ответ;
6. вошедший по приглашению **видит канал пространства** и **не видит чужих**.

Пункт 4 держится не проверкой в коде, а условием в самом изменении:
`UPDATE ... WHERE redeemed_at IS NULL AND revoked_at IS NULL AND expires_at > now()`.
Проигравший получает ноль изменённых строк. Проверка «а не занято ли»
отдельным запросом здесь была бы гонкой — той же, что мы уже ловили
в отправке сообщений.

## Чем платим

- **Одноразовость означает ссылку на каждого.** Пригласить десять человек —
  десять ссылок. Порог для многоразовой ссылки: когда владелец пожалуется.
  Многоразовая безопаснее не станет, поэтому по умолчанию её нет;
- **Почта уже занята — мы это скажем.** Регистрация и сейчас отвечает 409
  на занятый адрес, то есть по ней уже можно узнать, кто зарегистрирован.
  Вход по приглашению ведёт себя так же: **новую** утечку не заводим,
  старую здесь не чиним. Записано как долг, а не как «не заметили»;
- **Ссылка живёт в переписке.** Передал в чате — она там и осталась.
  Против этого работают срок и одноразовость, но не полностью.

## Как проверяется

Приёмочными тестами по живому стеку, по одному на каждый пункт списка выше.
Отдельно — что `register` **не** принимает токен ни под каким видом.
