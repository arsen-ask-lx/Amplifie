# Наши ошибки с realtime — и что из них выросло

Формат: **симптом** (как это выглядело) → **причина** → **лечение** → **чем ловить теперь**.
Ссылки в скобках — коммиты/задачи Audit Platform, для истории.

---

## 1. Новый канал без namespace → «не обновляется без F5»

- **Симптом:** бэкенд публикует, фронт подписывается, ошибок в консоли нет, но экран не обновляется.
  В логах Centrifugo `unknown channel`.
- **Причина:** канал `foo:user#42` требует namespace `foo` в `config.json`. Без него Centrifugo
  **молча** отклоняет и публикацию, и подписку.
- **Лечение:** каждый новый префикс канала сразу добавлять в `namespaces` конфига.
- **Чем ловим:** пункт чек-листа «швов проводки» + обязательная живая проверка (см. `03`).
  Идея для нового проекта: тест, который собирает все префиксы каналов из кода и сверяет с `config.json`.

## 2. Правка config.json не применилась (stale config)

- **Симптом:** namespace добавили, а `unknown channel` остался — и локально, и на проде.
- **Причина:** конфиг смонтирован в контейнер bind-mount'ом, а Centrifugo читает его **только на
  старте**. `docker compose restart` не помогает; `up -d` не пересоздаёт контейнер, если в compose
  ничего не поменялось.
- **Лечение:**
  - dev: `docker compose up -d --force-recreate centrifugo`;
  - prod: в env контейнера маркер `CFG_REVISION=${CENTRIFUGO_CONFIG_SHA}`, деплой считает
    `sha256sum centrifugo/config.json`. Хэш поменялся → compose сам пересоздаёт контейнер (b0cfb9e0).
- **Чем ловим:** маркер ревизии в деплое (`code-from-audit/infra/docker-compose.prod.centrifugo-snippet.yml`).

## 3. Уведомление создано, а колокольчик не звенит

- **Симптом:** запись уведомления в БД есть, в списке после F5 видна, но всплывашки нет.
- **Причина:** модуль документов делал `Notification.objects.create(...)` напрямую, мимо общей функции,
  которая после коммита отправляет пуш (task-178).
- **Лечение:** единственная дверь — `notify_user()`: пишет строку в БД **и** ставит пуш в `on_commit`.
  Прямое создание уведомлений запрещено правилом.
- **Чем ловим:** правило в скилле + инвентарь всех отправителей (`original-skill/references/notification-inventory.md`).
  Идея: grep-гейт на `Notification.objects.create` вне своего модуля.

## 4. Два издателя в коде

- **Симптом:** разные места публиковали по-разному: свои HTTP-запросы, свои ошибки, свои таймауты.
- **Причина:** realtime добавляли по фичам, каждый раз заново.
- **Лечение:** единый модуль `core/realtime.py` на официальной `cent`, API только keyword-only
  `publish(channel=, data=, idempotency_key=, raise_on_error=)` / `broadcast(channels=, ...)`,
  две типизированные ошибки `Retryable` / `NonRetryable` (task-177).
- **Чем ловим:** правило «из приложений — только `core.realtime`»; мёртвый второй издатель удалён (R5).

## 5. Цикл publish вместо broadcast

- **Симптом:** массовое действие над задачами тормозило.
- **Причина:** событие каждому причастному слалось отдельным `publish` в цикле: 500 задач × ~3 человека
  ≈ 1500 синхронных HTTP-запросов внутри одного запроса пользователя.
- **Лечение:** один `broadcast(channels=[...])`, один `event_id` на событие (R4). Ответ broadcast
  проверять **по каждому каналу** (`result.responses[i].error`), а не только по исключению.
- **Чем ловим:** тест `test_publish_uses_broadcast_not_publish_loop` (`code-from-audit/tests/tracker_test_realtime.py`).

## 6. Три–четыре WebSocket-соединения на вкладку

- **Симптом:** на странице 3–4 соединения и столько же запросов за токеном.
- **Причина:** каждый хук делал свой `new Centrifuge()` и свой `/connect/`.
- **Лечение:** модульный синглтон `centrifugoConnection.ts`: одно соединение, реестр подписок по
  каналу со счётчиком ссылок, `connectPromise` против гонки одновременного монтирования,
  `connectGeneration` против «зомби»-соединения старого пользователя при выходе во время подключения,
  `getToken` обновляет токен на реконнекте. Хук `useCentrifugoSubscription` поверх (task-181, R3).
- **Чем ловим:** правило «второе соединение в фиче не открывать».
- ⚠️ Исключение осталось: `versionRealtime.ts` держит **отдельное анонимное** соединение для
  `system:version` (до логина). В новом проекте реши это сразу (см. `04`).

## 7. Лишние subscription-токены

- **Симптом:** эндпоинт `/connect/` выдавал 6 токенов подписки, фронт их таскал.
- **Причина:** не разобрались в модели прав Centrifugo.
- **Лечение:** для user-limited каналов (`ns:name#<user_id>`, `allow_user_limited_channels`) хватает
  connection-токена с `sub`; для общих (`allow_subscribe_for_client`) — тоже. Sub-токен нужен только
  для приватных `$`-каналов. Отдаём один connection-JWT + имена каналов (R3).
- **Не путать:** «общий» namespace = **любой авторизованный** может слушать. Прав по пользователю нет.

## 8. Двойной тост

- **Симптом A:** одно уведомление всплывало дважды.
  **Причина:** `useNotifications` был смонтирован в двух местах, общее соединение раздавало событие
  обоим. **Лечение:** вся механика уведомлений — в одном синглтоне-контроллере, компоненты слушают
  через `useNotificationEvent(cb)` (ddedf6da). Промежуточную заплатку-дедуп удалили.
- **Симптом B:** после массового действия два одинаковых тоста.
  **Причина:** инициатору слали уведомление «применено N» поверх его же тоста на фронте.
  **Лечение:** актору не шлём уведомление о его собственном действии (1f69c26a).

## 9. Устаревшая карточка, хотя realtime работает

- **Симптом:** открыл карточку задачи повторно — показаны старые данные.
- **Причина:** подписка жила внутри модалки (`enabled: open`). Модалка закрыта → событие никто не
  слушает → кэш React Query не сброшен → повторное открытие в пределах `staleTime` отдаёт старьё.
- **Лечение:** один **всегда включённый** слушатель на сессию в корне приложения (`main.tsx`), выше
  всех веток роутера. Точечная инвалидация по id из события; на реконнект, `visibilitychange` и по
  фоновому таймеру ~120 с с разбросом — широкая инвалидация (task-218).
- **Почему нужен таймер:** Centrifugo может потерять публикацию **без разрыва** соединения — тогда ни
  реконнект, ни возврат во вкладку не сработают.

## 10. Событие адресовано не всем, кто видит данные

- **Симптом:** наблюдатель (директор, контроль качества) видит задачи проекта, но live-обновлений не получает.
- **Причина:** событие шлётся в личные каналы **причастных к задаче**, а экран показывает по праву
  доступа **к проекту**. Две разные модели доступа (task-219, открыт task-224).
- **Урок:** при проектировании канала сначала ответь «кто ВИДИТ этот экран», а не «кого касается
  объект». Канал на уровне объекта-контейнера (`tasks:project#id`) требует авторизации подписки —
  это уже приватный канал или proxy-подписка, иначе утечка чужих данных.

## 11. Событие не по порядку перезаписывало свежие данные

- **Симптом:** иногда в кэше оказывалась старая версия компании.
- **Причина:** события могут прийти не в порядке публикации (порядок гарантирован только для
  последовательных публикаций в один канал), а фронт писал payload прямо в кэш.
- **Лечение:** защита по `updated_at`: старее, чем в кэше, — игнорировать (87395a40).
  Ещё лучше — вообще не класть данные из события в кэш, а перечитывать REST.

## 12. Сбой публикации проглатывался молча

- **Симптом:** команда рассылки «вышла новая версия» при недоступном Centrifugo писала «успех».
- **Причина:** `publish(raise_on_error=False)` глотает ошибку внутри, а `except` снаружи не срабатывал никогда.
- **Лечение:** где важен исход — `raise_on_error=True` и честная обработка (87395a40).

## 13. Тесты зависели от окружения и ходили в сеть

- **Симптом 1:** контракт-тесты издателя проходили только на машине, где в `.env` есть ключ.
  **Причина:** без ключа издатель — тихий no-op, проверять нечего. Заплатку положили в env CI (c20089ef),
  то есть тесты стали зависеть от окружения.
  **Лечение:** фиктивные настройки в `settings/test.py` (адрес на домене `.invalid`), контракт-тесты
  строят `CentrifugoPublisher(api_url=, api_key=)` напрямую (f743382b).
- **Симптом 2:** в CI падал setup чужого теста (создание компании).
  **Причина:** Celery в eager-режиме + `transaction=True` → `on_commit` реально вызывал публикацию
  с `raise_on_error=True` → DNS-ошибка → `retry` → падение.
  **Лечение:** autouse-фикстура в корневом `conftest.py` глушит сетевую границу `cent.Client.publish/broadcast`
  для всех тестов (10050611). Файл: `code-from-audit/tests/conftest_stub_centrifugo_network.py`.
- **Симптом 3:** тест эндпоинта токена в CI отдавал 503.
  **Причина:** в CI не задан HMAC-секрет. **Лечение:** `override_settings` секрета в тесте (89639757).

## 14. Добавили `cent` — лёг весь стек

- **Симптом:** после пересборки контейнеры падают с `ModuleNotFoundError: cent`, дважды подряд.
- **Причина:** (1) пакет добавлен в `pyproject.toml`, но не в `uv.lock`, а образ ставит `uv sync --frozen`;
  (2) пересобрали `web`/`worker`, а у `bootstrap`/`init_permissions` свои образы — остались старые.
  `core.realtime` импортируется при старте приложения, поэтому упало всё.
- **Лечение:** `uv lock` + коммит обоих файлов; пересобирать **все** backend-сервисы.

## 15. Нет контура наблюдаемости у публикации

- **Факт (сверено с кодом):** издатель при сбое пишет только `log.error`. Нет событий
  `realtime.publish.start/ok/failed`, нет `duration_ms`, нет метрики Prometheus.
- **Следствие:** «Centrifugo лежит полдня» видно только по жалобам «не обновляется».
- **В новом проекте:** контур и метрика сразу (см. `02`, раздел «Наблюдаемость»).

## 16. Тосты «уведомление о том, что ты уже сделал»

- **Симптом:** человек скачал файл через 5 с, а уведомление «готово» пришло через 60 с и всплыло поверх работы.
- **Причина:** уведомление отправлял периодический обход раз в минуту; плюс всплывашка дублировала
  индикатор, который и так был на экране.
- **Лечение:** отправлять из места завершения (обход остаётся страховкой, дубль исключён условным
  обновлением `notified_at`) + флаг `quiet` у уведомления: «в ленту, без всплывашки» (32843a23, task-283).

## 17. Склейка уведомлений против 5-минутного дедупа Centrifugo — две ловушки подряд

Пачка однотипных действий («вам поставили задачу» ×7) заваливала колокольчик семью записями и семью
тостами. Лечение — склейка в корзину: одна запись с растущим `count` и дайджест-текстом (task-187,
`7fc2b32c`). По дороге вылезли две тихие ловушки, обе про идемпотентность:

- **Ловушка А (сервер).** Обновление корзины публикуется с ТЕМ ЖЕ `id` записи, а `idempotency_key`
  у нас был `str(id)` → Centrifugo видит «уже публиковали» и **молча глотает** второе, третье,
  седьмое обновление: счётчик на экране застывает на единице. Ключ обязан меняться вместе с
  содержимым: `f"{id}:{count}"` при склейке, `str(id)` у первого. Окно дедупа — 5 минут на канал,
  ровно в него и попадает любая пачка.
- **Ловушка Б (клиент).** Фронтовый дедуп по id теперь работает против нас: id прежний, payload
  новый. Для склеенных (непустой `coalesce_key`) дедуп по id **выключается**, иначе обновления
  счётчика отсекаются уже на клиенте. Тост обновляется на месте — у `sonner` `id = coalesce_key`,
  поэтому растёт один тост, а не семь.

**Урок шире Centrifugo:** идемпотентность — это «одно и то же не применится дважды», а не «один id —
одно сообщение». Как только под одним id поехало МЕНЯЮЩЕЕСЯ содержимое, оба дедупа (серверный и
клиентский) из защиты превращаются в потерю данных. Ключ дедупа обязан включать версию содержимого.

Гонку на создание корзины (два процесса — одна корзина) закрывает частичный уникальный индекс
`(user, coalesce_key) WHERE NOT is_read` плюс повтор веткой обновления на `IntegrityError`: арбитр —
БД, а не проверка «а нет ли уже» в питоне.

## 18. Апгрейд библиотеки-издателя может тихо убить ретраи

- **Факт:** в `cent` 5.2.0 **нет** класса `CentTimeoutError` — таймаут приезжает как
  `CentNetworkError`, и наш маппинг относит его к retryable. Верно. Но `CentTimeoutError` уже
  существует в неопубликованном `master` библиотеки.
- **Что будет при апгрейде:** новый класс не назван ни в одной ветке маппинга и упадёт в
  «неизвестная ошибка → non-retryable». Таймауты **перестанут ретраиться**, и ни один тест не
  покраснеет: тесты проверяют ровно те классы, что перечислены.
- **Лечение:** маппинг чужих исключений на свои перечитывать при КАЖДОМ апгрейде; пин по минорной
  ветке (`cent>=5.0,<6.0`); а лучше — тест, который берёт подклассы `CentError` из установленной
  библиотеки и краснеет, если появился класс, не названный в маппинге. Тогда апгрейд сам сообщает
  о новом виде отказа.

## 19. Payload из истории приезжает без полей, которых тогда ещё не было

- **Симптом-в-проекте:** добавили поле `quiet` («в ленту, без всплывашки»). Разбор на клиенте
  пересобирает объект по белому списку полей.
- **Ловушка:** у канала уведомлений история живёт 600 секунд. После обрыва связи клиенту законно
  прилетит публикация, сделанная **до выката**, — без нового поля. Значит умолчание выбирается не
  «как удобнее», а «как вело себя старое сообщение»: `quiet` по умолчанию `false`, то есть
  всплывает, как раньше.
- **Урок:** history/recovery означает, что схема payload всегда живёт в ДВУХ версиях одновременно —
  ровно `history_ttl` после каждого выката. Новые поля только с обратно совместимым умолчанием,
  поле `v` в payload — чтобы различие было видно, а не угадывалось.

# Что из этого уже про нас — сверка с нашим кодом 24.09.2026

Разбор по нашему дереву. Отмечено, где у нас то же самое сделано, где сделано
иначе, и где ловушка открыта.

## Уже закрыто у нас, и тем же способом

- **№ 4 «два издателя»** — у нас один: `backend/src/platform/bus.ts`, и звонок
  уходит только через него. Импорт шины из прикладных мест ловит гейт границ.
- **№ 6 «три-четыре соединения на вкладку»** — у нас одно соединение на вкладку
  (`frontend/src/data/liveStream.ts`) и явный предел открытых потоков на человека
  (`STREAM_OPEN`, task-093). Число открытых труб — наблюдаемое (`amplifie_streams`).
- **№ 9 «слушатель внутри модалки»** — наш слушатель живёт в `useChat` и не
  зависит от того, что открыто на экране; страховка по возврату во вкладку
  и повтор после обрыва написаны отдельно (task-093).
- **№ 12 «сбой публикации проглатывался»** — `publish` у нас **никогда не
  отвергается**, но и не молчит: всякий отказ уходит объявленному сообщателю,
  а падения слушателей считаются (`amplifie_listener_failures_total`).

## Сделано иначе — и, похоже, надёжнее

- **№ 11 «событие не по порядку перезаписало свежее»** — у них защита по
  `updated_at`. У нас жёстче: реплика из события применяется, **только если её
  номер продолжает курсор клиента** (`frontend/src/data/carried.ts`), иначе
  вкладка идёт в догон. Дыра в номерах лечится не догадкой, а запросом.
- **№ 7 «лишние токены подписки»** — у нас подписки как понятия нет: поток один
  на пространство, а кому какой разговор виден, решает сервер при рассылке
  (`resolveAudience` в шине). Токенов на подписку не существует.

## Открытые ловушки — те же самые, и они про нас

- **№ 10 «событие адресовано не всем, кто видит данные».** Наш разрешитель
  адресатов отвечает на вопрос «кому виден разговор». Ровно этот вопрос и
  правильный — но он задаётся про **разговор**, а панель показывает ещё и
  счётчики папок, и «Недавние». Если появится экран, который показывает данные
  по праву доступа к **проекту**, адресация по разговору начнёт врать —
  как у них с наблюдателем, который видит проект, но не получает обновлений.
- **№ 19 «payload из истории без новых полей» — прямо наш случай.** У нас
  хвост изменений живёт в памяти процесса (`backend/src/platform/tail.ts`,
  512 записей). После выката в хвосте лежат записи, собранные **старым** кодом.
  Значит новое поле в `changeEvent` обязано иметь обратно совместимое умолчание,
  а не «как удобнее». Сегодня в контракте поля версии нет.
- **№ 17 «дедуп против склейки».** У нас дедуп по `clientMsgId` при отправке
  и по `id` при слиянии ленты. Пока под одним идентификатором едет
  неизменяемое содержимое, это защита. Как только под тем же `id` поедет
  меняющееся (счётчик, склейка уведомлений) — та же защита станет потерей.
- **№ 15 «нет контура наблюдаемости у публикации»** — у нас есть счётчики
  событий и падений, но **нет времени** раздачи и нет причины отказа меткой.
  При 3000 вкладках секунда задержки нашлась по `amplifie_event_loop_lag_seconds`,
  а не по метрике раздачи.

## Что из их гейтов стоит завести у нас

- сверка «все префиксы каналов из кода объявлены в конфиге» — у нас аналога
  нет, потому что нет каналов; **если возьмём Centrifugo, гейт заводить в тот
  же день**, иначе первая же новая дверь молча замолчит;
- тест, который краснеет при появлении **неназванного** класса ошибок в чужой
  библиотеке (их № 18). У нас та же порода: разбор отказов сервера живёт
  в `frontend/src/shared/trouble.ts` и молча относит незнакомое к «прочему».

## Общий вывод, ради которого это перенесено

Их же строкой: почти все ошибки — швы проводки, и юнит-тесты с подделками
были зелёными во всех случаях. У нас это правило уже оплачено кровью дважды:
прибор нагрузки шесть раз мерил сам себя (task-091), а заглушка в конфиге
прокси прожила неделю незамеченной. Поэтому у нас проверки идут по собранному
образу и живому стеку — и при переходе на любой новый транспорт это
требование не ослабляется, а усиливается.
