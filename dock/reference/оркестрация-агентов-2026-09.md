# Оркестрация агентов: как делают другие и как работаем мы — 27.09.2026

Вопрос владельца: как топовые команды раздают работу агентам, какую модель ставят на какой
этап, правильно ли в `audit_project` роли из `.claude/agents` превращены в скиллы и что
оттуда взять к нам. Разбор — пять подагентов параллельно (веб, документация Claude Code,
конвейер `audit_project`, его гейты, его скиллы). Ключевые поля Claude Code я сверил
по документации сам.

## 1. Что делают другие — факты с источником

- **Anthropic, исследовательская система**: ведущий на Opus планирует и режет задачу,
  3–5 подагентов на Sonnet идут параллельно, каждый в своём контексте. На их замере это
  на 90,2% лучше одного Opus, но в ~15 раз дороже по токенам. Первые версии плодили
  до 50 подагентов на простой вопрос и дублировали работу.
  [источник](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Anthropic, «Building effective agents»**: начинать с простейшей схемы, автономию
  наращивать, только когда есть чёткий критерий успеха.
  [источник](https://www.anthropic.com/engineering/building-effective-agents)
- **Cognition (Devin)**: сначала «не стройте мультиагентов» — параллельные писатели
  принимают несогласованные решения. Позже — что работает: **запись в один поток,
  а дополнительные агенты дают ум, а не действия**. Ревьюер с чистым контекстом (без
  истории задачи) находит в среднем 2 ошибки на PR, 58% из них серьёзные.
  [раз](https://cognition.com/blog/dont-build-multi-agents),
  [два](https://cognition.com/blog/multi-agents-working)
- **OpenAI Agents SDK**: два вида делегирования — передать разговор целиком (handoff)
  или позвать агента как инструмент и забрать результат.
  [источник](https://openai.github.io/openai-agents-python/multi_agent/)
- **Claude Code**: `opusplan` — Opus в режиме плана, Sonnet на исполнении; agent teams —
  экспериментально, советуют 3–5 участников и не советуют для последовательной работы
  и правок одних файлов. [модели](https://code.claude.com/docs/en/model-config),
  [команды](https://code.claude.com/docs/en/agent-teams)
- Вторичные источники (не сверены с первоисточником): у Amp дорогая модель-«оракул»
  только советует и ревьюит, а код пишет основная; у Jules план делает Gemini Pro,
  а мелкие шаги — Flash.

**Сходится у всех:** дорогая модель — там, где решение (план, спорная развилка, итоговая
оценка); дешёвая — на объёме (поиск, механические правки, прогоны). Параллелить анализ,
а не запись в одни и те же файлы. Ревьюер — со свежим контекстом.

## 2. Подагент или скилл — по документации Claude Code

| | Подагент `.claude/agents/*.md` | Скилл `.claude/skills/*/SKILL.md` |
|---|---|---|
| Контекст | свой, чистый; главному возвращается сжатый итог | общий с сессией; `context: fork` — в отдельном |
| Модель | `model: opus / sonnet / haiku / inherit` на все его шаги | `model:` — только на текущий ход |
| Инструменты | `tools:` / `disallowedTools:` — жёстко | `allowed-tools` — разрешения на ход, не ограничение |
| Скиллы внутри | `skills: [...]` — подгружаются при старте | — |
| Прочее | `effort`, `memory`, `isolation: worktree`, `maxTurns`, `background` | `paths:` — включается по файлам |

Источники: [подагенты](https://code.claude.com/docs/en/sub-agents),
[скиллы](https://code.claude.com/docs/en/skills).

**Про `audit_project`.** 25.09 все 13 агентов удалены коммитом «субагентов нет — роли
исполняет главная сессия через скиллы». Причина верная: агенты были байт в байт копиями
скиллов, и две копии расходились. Но вместе с копией ушли свой контекст у ревьюера,
модель по роли (Opus на план и ревью, Sonnet на сборку) и жёсткий список инструментов —
в восьми скиллах так и записано: «прежний frontmatter агента не воспроизводится».

**Как взять оба плюса.** Знание и порядок работы — в скилле, одна копия. Роль — тонкий
файл агента на десяток строк: модель, инструменты и `skills: [этот скилл]`, без
повторения текста. Дублирования нет, изоляция и модель остаются.

## 3. Что берём из `audit_project`

Сделать сейчас:
- **Сторож «CI красный — сначала разбор»** (их хук `require-ci-analysis.sh` на `glab`):
  у нас это правило записано только словами. Переводим на `gh`.
- **Скилл k6**: ловушки первого замера и что переносится на прод. k6 у нас стоит,
  скилла нет.
- **Раздел «Fail-open» из их security-review**: секрет со значением по умолчанию,
  отладка включена по умолчанию, порядок поиск → проверка → подтверждение. Не зависит
  от стека, у нас его нет.

Позже — каждое отдельным решением, это новые инструменты:
- gitleaks вместо своего `secrets-not-in-code`; hadolint для двух Dockerfile;
  semgrep с готовыми правилами TS как совещательный гейт;
- замок на тесты (`test-lock`): механически ловит правку теста исполнителем.
  У нас это правило держится словами («исполнитель не ослабляет свой тест»);
- граф кода по MCP (codegraph) — только после отдельного замера пользы.

Не берём:
- восьмиступенчатый конвейер с Auditor, JiTTest, Sentinel, Evolver, Doc-Architect —
  он рассчитан на их масштаб; у нас «простое надёжнее сложного»;
- самоправку промптов (Evolver) — у нас процесс меняет только слово владельца;
- хук автоформата, mutmut, `.importlinter`, общие скиллы Docker и миграций — у нас
  уже есть свои, не хуже.

## 4. Как работаем с 27.09 (предложение, ждёт одобрения — task-126)

| Этап | Кто | Модель | Почему |
|---|---|---|---|
| План, развилки, итоговое решение | главная сессия | Opus | решение дороже всего в откате |
| Критик плана | агент `plan-critic` | Opus | редкий и самый ценный взгляд; свежий контекст |
| Ресёрч, поиск по коду, списки кандидатов | подагенты параллельно | Sonnet | объём, только чтение |
| Красный тест и код | главная сессия; механический объём — подагенты по непересекающимся файлам | Opus / Sonnet | запись в один поток на файл (Cognition) |
| Ревью набора правок | агент `reviewer` | Sonnet | свежий контекст и другая модель, не автор |
| Ревью рискованного (права, данные, протокол) | агент `reviewer` | Opus | цена пропуска выше лимита |

Правила: параллельные писатели — только на непересекающихся файлах, а общие
(`Makefile`, `package.json`, карта) правит главная сессия. Больше пяти подагентов разом —
только когда задач правда столько. Главная сессия не пересказывает найденное, а сверяет
ключевое сама — отчёт агента не доказательство.
