# Поиск по сообщениям — разбор 17.09.2026

Два узких вопроса: **что делает поиск Телеграма удобным** и **как искать
по 10 млн сообщений в одном Postgres, не заводя отдельный поисковый сервер**.
Метка **[вывод]** — моё заключение, в источнике прямо его нет; всё
остальное взято из ссылки рядом.

## 1. Телеграм

### Удобство — в поведении экрана, а не в совпадении слов

- поиск внутри чата показывает «n из N» и ходит по находкам стрелками;
  F3 / Shift+F3 в Telegram Desktop — [блог 2015](https://telegram.org/blog/search-and-media),
  `history_view_compose_search.cpp` в [tdesktop](https://github.com/telegramdesktop/tdesktop/tree/dev/Telegram/SourceFiles);
- переход к найденному открывает историю с якорем на сообщении и подсвечивает
  слово; дойдя до края загруженных находок, клиент сам догружает следующую
  страницу (`searchMore()`);
- порядок — от новых к старым: «in order of decreasing message_id»
  ([TDLib searchChatMessages](https://core.telegram.org/tdlib/docs/classtd_1_1td__api_1_1search_chat_messages.html));
- фильтры сочетаются: по типу, по дате текстом, по источнику
  ([блог 2020](https://telegram.org/blog/filters-anonymous-admins-comments));
- страница — 50 (`kSearchPerPage = 50`); пауза перед запросом при наборе —
  900 мс (`kSearchRequestDelay`); первая страница кешируется по строке
  запроса, новый запрос отменяет старый (`dialogs_widget.cpp`).

### Совпадение у них простое и местами неточное

- совпадают **целые слова**, кусок из середины не находится: «gram» не находит
  «Telegram» ([tdesktop #7942](https://github.com/telegramdesktop/tdesktop/issues/7942),
  [#1714](https://github.com/telegramdesktop/tdesktop/issues/1714));
- счётчик найденного **неточный по договору**: флаг `inexact` в
  [messages.messagesSlice](https://core.telegram.org/constructor/messages.messagesSlice);
- морфология, ё/е и поиск по началу слова **не описаны нигде** — серверный
  поиск закрыт;
- локальный поиск TDLib (только секретные чаты) — SQLite FTS5 по целым словам
  без `*` ([MessageDb.cpp](https://github.com/tdlib/td/blob/master/td/telegram/MessageDb.cpp)).

**[вывод]** Копировать надо поведение экрана. Совпадение решаем сами:
владелец 17.09 выбрал «слова, формы и начало слова».

## 2. PostgreSQL 18

- **ранг не нужен**, когда порядок — по времени: `ts_rank` читает вектор
  каждого совпавшего документа; `ts_headline` работает по исходному тексту
  и медленный — только на итоговой странице
  ([textsearch-controls](https://www.postgresql.org/docs/18/textsearch-controls.html));
- **конфигурация `russian`** сама разводит латиницу в `english_stem`,
  кириллицу в `russian_stem` ([textsearch-psql](https://www.postgresql.org/docs/18/textsearch-psql.html));
  **[вывод]** начало слова надёжнее искать по второму вектору `simple` с `:*`:
  основа обрезанного слова может не совпасть;
- **`слово:*`** ищет по началу лексемы; у `websearch_to_tsquery` такого
  синтаксиса нет — запрос собирается самим, словами из букв и цифр;
- **главная ловушка:** GIN не отдаёт строки в порядке даты. Для частого
  слова база находит все совпадения, читает и сортирует их ради 20 строк
  ([mydba.dev](https://mydba.dev/blog/postgres-full-text-search-tsvector-gin),
  [рассылка pgsql](https://www.postgresql.org/message-id/4A6247BC.2070108%40krade.com));
- **цена записи:** `fastupdate` копит вставки в список ожидания; вставка,
  переполнившая его, чистит список сама и заметно медленнее; советуют
  чистить автовакуумом и настраивать `gin_pending_list_limit` на индекс
  ([gin.html](https://www.postgresql.org/docs/18/gin.html));
- **миграция:** `ADD COLUMN … GENERATED STORED` переписывает таблицу под
  исключительной блокировкой ([ALTER TABLE](https://www.postgresql.org/docs/18/sql-altertable.html));
  живой пример — больше 18 часов на 50 млн
  ([рассылка](https://www.postgresql.org/message-id/03C74523-7947-42CA-8392-B7CB8EFC16D2%40gmail.com));
- **pg_trgm** (кусок из середины, опечатки): индекс сравним с таблицей,
  на 9,7 млн файлов запросы 7–28 с
  ([hexops](https://github.com/hexops-graveyard/pgtrgm_emperical_measurements));
- **RUM** умеет порядок по дате внутри индекса; поддержка PG 18 с 1.3.15,
  запись дороже GIN, были ошибки корректности
  ([rum](https://github.com/postgrespro/rum), [Postgres Pro 18.3.1](https://postgrespro.com/docs/postgrespro/current/release-pro-18-3-1));
  в alpine-образ — собирать самим;
- **ParadeDB pg_search** — AGPL-3.0, `shared_preload_libraries`, тянет
  pgvector, сборок под alpine нет ([paradedb](https://github.com/paradedb/paradedb)).

## 3. Как делают другие мессенджеры

| Кто | Как | Чем обожглись |
|---|---|---|
| Zulip | вектор в таблице сообщений, GIN; пересчёт фоном по журналу | встроенный поиск только английский; PGroonga экспериментальна ([docs](https://zulip.readthedocs.io/en/latest/subsystems/full-text-search.html)) |
| Synapse | **отдельная таблица** `event_search`, GIN + btree `(room_id, ts, ordering)`, права — `room_id IN (…)`, страницы по ключу, `ts_headline` | вставка в таблицу поиска занимала 30+ с синхронно с отправкой ([#4219](https://github.com/matrix-org/synapse/issues/4219)) |
| Mattermost | Postgres FTS, затем Elasticsearch | деградация около 2 млн постов на их схеме; конфигурация в запросе не совпала с индексом — индекс не работал ([docs](https://docs.mattermost.com/administration-guide/scale/enterprise-search.html), [#2622](https://github.com/mattermost/mattermost/issues/2622)) |
| Rocket.Chat | текстовый индекс MongoDB | поиск в одной комнате обходил индекс всех — падения; починили, поставив комнату первым ключом ([PR 40397](https://github.com/RocketChat/Rocket.Chat/pull/40397)) |
| Discord | Elasticsearch, шард на сервер | очередь теряла сообщения, узел ронял пачки записей ([блог](https://discord.com/blog/how-discord-indexes-trillions-of-messages)) |

**Уроки для нас:**

1. область доступа — ведущий ключ, а не фильтр после (Rocket.Chat, Synapse);
2. отдельная таблица поиска не трогает горячую таблицу сообщений (Synapse);
3. цену записи в индекс мерить хвостом задержки отправки, а не средним (Synapse #4219);
4. страницы — по ключу, не смещением; ранг не считать при порядке по времени;
5. отдельный поисковый сервер — масштаб Discord, не наш: у Discord он принёс
   ровно тот класс поломки (потеря записей очередью), от которого у нас
   защищает одна транзакция.

## 4. Варианты под наши условия

| | Что | За | Против | Когда |
|---|---|---|---|---|
| **A** | встроенный поиск: отдельная таблица, GIN, векторы `russian` + `simple` | ничего нового; путь Synapse | частое слово дорого без приёма; нет куска из середины | по умолчанию |
| **B** | A + RUM | порядок по дате в индексе | расширение, своя сборка образа, запись дороже, были ошибки | если замер A провален |
| **C** | pg_trgm | кусок из середины, опечатки | индекс с таблицу, медленно на 10 млн | отвергнут владельцем 17.09 |
| **D** | Elasticsearch / Meilisearch | масштаб | второй узел, рассинхрон, очередь — противоречит «нет очереди» | за пределами цели Р-038 |

**Рекомендация:** A, решение о порядке выдачи для частого слова — **замером
на засеянных 10 млн до кода** (task-100, шаг 0). B — только по проваленному
замеру.
