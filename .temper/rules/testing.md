# Тесты

## Главное правило

**Поведение важнее реализации.** Основной тест доказывает наблюдаемый результат через внешний
интерфейс: запрос → ответ и состояние системы.

Критерий отбора: «переписали реализацию, поведение то же — тест выжил?» Нет — переписать на
поведение или удалить.

## Порядок

1. приёмочный тест насквозь — **первым, красным**;
2. код до зелёного;
3. точечные тесты только на нетривиальную чистую логику: расчёты, разборщики, преобразования.

Тест на связующий код, который уже покрыт поведенческим, — **запрещён**: он ломается при любой
правке и ничего не доказывает.

## Интерфейс: сценарий проверяет, что человек делает и видит

Сценарий интерфейса проверяет **действие и его результат**: выбрал — выбор встал; нажал
Escape — закрылось; перезагрузил — сохранилось; прочитал нужный текст; дотянулся до кнопки.

**Значения CSS и пиксели сценарий не проверяет** — скругление, рамку, тень, отступ, точный
размер шрифта, ширину колонки. Такой тест не проходит главный критерий: поменяли дизайн,
человек ничего не потерял, а тест покраснел. Красный без поломки учит не верить красному.

Геометрия допустима в одном случае — **когда она ломает пользование**: окно не влезает в узкий
экран, кнопку не нажать, время налезает на текст и его не прочесть. Проверяется сам факт
(«не налезает», «влезает»), а не число из макета.

**Единообразие вида держит общий источник, а не тест.** Два элемента обязаны совпадать —
у них одно значение из токена или общего модуля (`shared/ui/quiet-field.ts`), и разъехаться
им не из чего. Цвет — только из токена, это стережёт гейт `color-from-token`. Вид, который
нельзя свести к источнику, проверяет глаз владельца по снимку, а не сценарий.

📏 11.09.2026 сценарий «поле и список — одна визуальная система» покраснел на правке дизайна
полей (24px против 18px), хотя ничего не сломалось. Причина была не в тесте, а в трёх копиях
одной строки стилей с `!important` — список о них не знал. Лечение — общий источник; тест
с пикселями убран.

## Вопросы к тестам пишутся до тестов

Сначала — список словами: «что именно мы проверяем и почему это важно». Он живёт в плане и
одобряется вместе с ним. Только потом из него делаются тесты, один вопрос на один-пять тестов.

Без этого шага тесты пишутся под уже написанный код и проверяют его же: они зелёные, а задача
не проверена. Список словами человек читает и спорит с ним; список тестов — не читает.

**Бюджет:** примерно один тест на двадцать изменённых строк. Вышел за него — либо задача
велика для одного набора правок, либо тесты проверяют реализацию.

## Чистка после зелёного

Зелёный набор — не повод оставить всё, что написано по пути. Тест, который ломается при
переписывании реализации и ничего при этом не доказывает, удаляется **до** вливания.

Иначе тесты растут быстрее кода, и через полгода их никто не решается тронуть: непонятно,
какой из них что стережёт.

## Старый код — не арбитр

Сверка нового поведения со старым доказывает **совместимость, а не правильность**. Если старое
считало неверно, новое совпадёт с ним и подтвердит ошибку.

Арбитр обязан быть **независимым**: официальный источник, документ от заказчика, ручной
пересчёт, живая система. «Совпало с прежним» — результат сверки, а не доказательство.

📏 На соседнем проекте девять сверок подряд показали «совпадает» — на данных, которые обе
стороны считали неверно.

## Арбитр нельзя подгонять

Тот, кто чинит код, не правит тест, который этот код проверяет. Механически: снимок тестов до и
после работы агента; расхождение — разбор, а не «наверное, безобидно».

Нейросети правят и удаляют мешающие тесты — это измеренное поведение, а не подозрительность.

## Запрещено

- `assert true` и проверки «не пусто» вместо точного значения;
- тихий пропуск теста;
- проверка записи в лог вместо проверки поведения;
- имена по номеру тикета — расширяй тематический файл;
- больше десяти подделок в одном файле: столько подделок означает, что тест проверяет сам себя.

## Живой прогон перед сдачей

Для всего, что ходит наружу — очереди, внешние сервисы, файлы, реальное время: прогнать своими
руками по-настоящему, как пользователь, и посмотреть логи всех сторон. Тесты с подделками
структурно слепы на швах: настройки, перезапуски, регистрация задач.
