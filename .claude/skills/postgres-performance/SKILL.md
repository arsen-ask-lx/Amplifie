# Производительность Postgres — как у нас

## 0. Факты проекта (сверено с кодом 16.09.2026) — читать первым

- **Postgres 18** (`postgres:18-alpine`), **drizzle-orm** поверх `pg`. Запросы
  к таблицам — только в `repo.ts` модуля-владельца; это стережёт `make arch`.
- **Пул один на процесс:** `max: 10`, `connectionTimeoutMillis: 5000`
  (`backend/src/platform/db.ts`). Нет свободного соединения 5 с — запрос
  падает с 500. Очередь видна метрикой `amplifie_pool_waiting`, занятость —
  `amplifie_pool_busy`.
- **Счёт запросов на каждый HTTP-запрос** — `AsyncLocalStorage` в `db.ts`;
  на стенде сервер отдаёт заголовок `x-db-queries`. Процессный счётчик —
  `amplifie_db_queries_total`. Их расхождение ловит враньё прибора.
- **Каждый запрос человека стоит двух обращений на сессию** (Д-39) — учитывай
  это в любой оценке «сколько запросов у двери».
- **Арбитры цены:**
  - `backend/tests/query-budget.e2e.test.ts` — бюджет запросов у дверей
    (отправка — 12, разобрано поимённо в тесте);
  - `make cost` — сколько **строк** читает горячий запрос; сеет 50 000 реплик
    в транзакции с откатом и сравнивает два объёма. Меряет прирост, а не время:
    время зависит от соседа по машине;
  - `make event-cost` — цена события не растёт с числом вкладок;
  - `make load` — нагрузка; выше тысячи вкладок — изнутри сети стенда
    (`tools/load/measure.mjs`, заголовок).
- **`pg_stat_statements` не включён.** Включать — отдельной задачей.
- Консоль базы — `make psql`.

## 1. Прежде чем добавлять индекс

Индекс — не лекарство «на всякий случай»: каждая запись обновляет все индексы
таблицы, а у нас запись в пространство и так стоит в очереди на строке
`workspace.last_seq` (Д-2).

1. Найди настоящий SQL: у построителя drizzle есть `.toSQL()` — им пользуется
   `make cost`. Не переписывай запрос руками для замера: копия разойдётся.
2. Посмотри план на **засеянной** базе (`make scale-seed`, затем `make psql`):
   ```sql
   EXPLAIN (ANALYZE, BUFFERS) <запрос с подставленными значениями>;
   ```
   На пустой базе обход неотличим от индекса — такой план ничего не доказывает.
3. Индекс добавляется, только если план показывает `Seq Scan` по большой
   таблице или `Rows Removed by Filter` в тысячах — и красный `make cost`
   до правки.

### Когда индекс бесполезен

| Ситуация | Почему |
|---|---|
| таблица до нескольких тысяч строк | обход дешевле похода по индексу |
| колонка с двумя-тремя значениями | индекс почти ничего не отсекает |
| уже есть составной `(a, b)`, а ищем по `a` | ведущая колонка составного уже работает |
| колонка редко в `WHERE`, `JOIN`, `ORDER BY` | место и цена записи без пользы |

### Какой индекс

- **B-tree** — по умолчанию: равенство, диапазоны, сортировка. Порядок колонок
  составного: сначала равенство, потом диапазон/сортировка
  (у нас `message_workspace_updated_seq_idx` = `(workspace_id, updated_seq)`).
- **Частичный** (`WHERE ...`) — когда запрос всегда отсекает большую часть
  строк одним условием (например, `deleted_at IS NULL`).
- **Покрывающий** (`INCLUDE`) — когда ответ целиком из индекса и нужен
  `Index Only Scan`.
- **GIN** — массивы, `jsonb`, полнотекстовый поиск; **pg_trgm** — `ILIKE '%x%'`.

## 2. Как читать план

| Признак | Что значит |
|---|---|
| `Index Only Scan` | ответ из индекса, таблица не читается — лучше всего |
| `Index Scan` | нашли по индексу, дочитали строки |
| `Bitmap Heap Scan` | средняя доля строк — нормально |
| `Seq Scan` на большой таблице | нет подходящего индекса или условие его не использует |
| `Rows Removed by Filter` в тысячах | индекс неточный — в составной не хватает колонки |
| `Nested Loop` с `loops` в сотнях | N+1 внутри базы |
| оценка `rows` отличается от `actual` в 10+ раз | устарела статистика — `ANALYZE таблица` |
| `Sort Method: external merge Disk` | сортировка на диске — не хватает `work_mem` или индекса под `ORDER BY` |
| `Buffers: shared read` велико | читаем с диска, а не из кеша |

## 3. Приёмы запросов, проверенные у нас

- **Подзапрос с `LIMIT` вместо агрегата по всей переписке.** Последняя
  активность — `ORDER BY seq DESC LIMIT 1` по индексу `(conversation_id, seq)`,
  а не `MAX(created_at)` по каналу (Д-30).
- **`LIMIT` как граница внутри счёта.** Непрочитанное считает не больше тысячи
  строк после отметки, и только среди них отсеивает своё и удалённое: условия
  через границу не перетекут, и план не уйдёт в обход (`unread.ts`).
- **Подзапрос `EXISTS`, а не соединение,** когда список не должен размножаться
  (`pinned` в `listConversationsFor`).
- **Одна строка сверх лимита вместо `COUNT(*)`** для «есть ли ещё» (`pageOf`).
- **Курсор по значению, а не смещение** — `before`, `after`: смещение съезжает
  от новых строк и дорожает с глубиной.
- **Чтение для ответа — за фиксацией:** под замком строки пространства только
  то, без чего запись неполна (task-082).
- **Условие по арендатору — отдельным `eq(workspaceId)`,** даже если видимость
  его подразумевает: видимость проверяет строку, а не отбирает.

## 4. Пул и очередь

- Пул из десяти выбран под одного разработчика и не пересматривался (Д-39).
  Размер считают от ядер Postgres, а не «побольше»: лишние соединения
  не ускоряют базу, а делят её процессор.
- **Очередь к пулу — главный признак перегрузки,** а не занятость. Выросла
  очередь — смотри, кто стадом ходит в базу (замер task-091: 1 561 → 6 133
  ожидающих за три секунды при волне догонов).
- Долгий запрос держит соединение — одна тяжёлая дверь без предела страниц
  отнимает пул у всех (Д-41).

## 5. Порядок работы

1. Замер до правки: `x-db-queries` двери, `make cost`, при необходимости
   `make load`. Число — в журнал плана.
2. Красная проверка: бюджет в `query-budget.e2e` или сценарий в `check-cost`.
3. Правка запроса или индекса (индекс — миграцией, см. скилл `safe-migrations`).
4. Тот же замер после, два прогона, условия названы.
