# Нагрузочный прогон k6

> Перенесено 27.09.2026 из audit_project (`.claude/skills/k6-load-testing/`), адаптировано
> под наш стек: два сценария на нашем стенде вместо одного на Django/ASGI, свой набор
> ловушек из `task-122` и `Р-051` вместо чужих (там их не было).

Два сценария, оба поверх Caddy на живом стенде:

```bash
make up                                      # стенд поднят — обязательно
make conditions                              # тихо ли на стенде — перед тяжёлым прогоном
make k6                                      # двери чтения: panel/feed/sync_hot/sync_cold/search
make k6-sse                                  # доставка до чужой вкладки
make k6-compare                              # сверка k6 и своего прибора на одних условиях

RATE=10 DURATION=30s PEOPLE=10 P99_MS=1500 make k6     # настройки — переменными
TABS=20 RATE=5 SEND_S=20 make k6-sse                   # не SECONDS: занята оболочкой (см. ловушки)
```

Код выхода k6 ненулевой при нарушенном пороге — это и есть вердикт; читать числа
до вердикта смысла нет.

## Что где лежит и почему так

| Что | Где | Зачем именно так |
|---|---|---|
| двери чтения | официальный образ `grafana/k6:2.3.0` по отпечатку | никакой сборки, воспроизводимо |
| доставка (поток) | свой образ `tools/load/k6/Dockerfile`: `grafana/xk6` + `xk6-sse@v0.2.0` по закреплённым версиям | автоматическое разрешение расширений k6 2.x тянуло бы чужую сборку на лету — отвергнуто Р-051 |
| сценарии | `tools/load/k6/reads.js` (двери), `tools/load/k6/delivery.js` (доставка) | свой код, ни строки из `tools/load/stand.mjs` — иначе сверка ничего не доказывала бы |
| второй прибор для сверки | `tools/load/measure.mjs`, режим `SYNC=0` | вкладки k6 не повторяют клиента (догон, панель) — третья копия поведения клиента разошлась бы, как две первые (task-091) |
| сеть | `amplifie_default` через `caddy:80` | путь как у настоящего клиента; подделка `X-Forwarded-For` запрещена |

## Как читать итог

1. **Вердикт — код выхода.** Порог нарушен → k6 сам печатает какой и выходит ненулевым
   кодом; числа рядом читать бессмысленно, если вердикт уже красный.
2. **`own_rate_limit` (счётчик 429) — не провал сервера.** `http.setResponseCallback`
   в обоих сценариях не засчитывает 429 в `http_req_failed`; порог `own_rate_limit ==
   0` отдельно ловит, если замер упёрся в свой же лимит частоты, а не в сервер.
3. **`dropped_iterations == 0`.** Если сервер встал, k6 молча роняет часть проходов —
   без этого порога 0.99 посчитался бы по меньшей, уже отфильтрованной выборке.
4. **`streams_opened == TABS`, `streams_late == 0`** (только `delivery.js`) — вкладка,
   опоздавшая открыть поток к началу отправки, недосчитала бы доставки по вине
   прибора, а не сервера.
5. **`ИТОГ-JSON` в конце вывода** — одна строка со сводкой (`tabs`, `sent`, `delivered`,
   `share`, `sendMs`, `deliveryMs`), которую читает `make k6-compare`; заменяет
   встроенную таблицу k6 (она требует библиотеку из сети).
6. **`make k6-compare`** сверяет k6 и свой прибор на одних условиях: код 0 у обоих,
   объём не пустой и равный, доля доставки совпадает до 1 п.п., ответ на отправку —
   в пределах 20% (`task-122`, П-3). Разошлись — это находка, а не повод подгонять.

## Что переносится на прод, а что нет

| Переносится | НЕ переносится |
|---|---|
| растёт ли время с числом вкладок/людей при той же загрузке машины | абсолютные миллисекунды с ноутбука владельца |
| упирается ли прогон в свой же лимит частоты раньше сервера (`own_rate_limit`) | сколько людей выдержит прод |
| доля доставки и время доставки до чужой вкладки — впервые измерены (`delivery.js`) | поведение при пересечении пиков на прод-хосте |
| было → стало после правки при похожей загрузке | сборка своего образа на CI — там официальный `reads.js` без расширения |

По проду нагрузку не пускаем — там люди; числа только со стенда.

## Ловушки первого замера (наши, из task-122)

1. **`SECONDS` — переменная оболочки, не наша.** `${SECONDS:-20}` в `make k6-sse` давал
   0 и k6 отказывался стартовать; переменная называется `SEND_S`, не `SECONDS`.
2. **Общий номер прохода, не `__VU`/`__ITER`.** `__ITER` у разных VU совпадает — при
   раскладке людей или отправителей по нему они шли неровно (480 лишних отказов по
   своему порогу на одном человеке, 27.09). Раскладка — по
   `exec.scenario.iterationInTest`.
3. **Пороги частоты — копия `backend/src/surface/http/limits.ts` (Р-025), а не
   отдельная догадка.** Разойдутся — прогон упрётся в свой лимитер, а не в сервер;
   `own_rate_limit` и печатает это отдельно, счётчик не даёт молча соврать.
4. **Обход лимитера через `X-Forwarded-For` запрещён.** Стенд верит заголовку от
   соседей по сети (`trustProxy`), и k6 обязан ходить только через `caddy:80`, как
   настоящий клиент, — иначе замер мерит не то, что увидит пользователь.
5. **Поиск и догон — не «одна дверь».** Пустой канал в поиске отвечает мгновенно и не
   мерит ничего (найдено ревью 27.09) — `setup()` заводит каналы со словом «k6».
   Догон — две двери: у головы (ответ из памяти) и с нуля `after=0` (из базы); одна
   дверь молчала бы про самый частый путь.
6. **`# syntax=docker/dockerfile:1` тянет описание синтаксиса из сети на каждую
   сборку** — без интернета `make k6-sse` падал; строки в `tools/load/k6/Dockerfile`
   нет, особых возможностей BuildKit файлу не нужно.
7. **Без сигнала «стоп» вкладки `delivery.js` не виснут навечно**, но тянут прогон до
   `maxDuration` — сигнал (реплика-маркер) обязателен, иначе долгий прогон вместо
   быстрого красного.
8. **Первый прогон сверки может поймать ошибку в самом сценарии k6, не в продукте** —
   счётчик своего порога (`own_rate_limit`) для того и стоит первым, что проверяется.
