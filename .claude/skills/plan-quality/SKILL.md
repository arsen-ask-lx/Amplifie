# Качество плана: что проверить, прежде чем просить одобрения

Шаблон и обязательный состав плана — в правилах планов проекта (ссылка
«Правила плана» в корневом `AGENTS.md`). Здесь **не второй шаблон**, а проверки,
без которых план выглядит полным и при этом пропускает дорогие ошибки.

## 1. Сначала найди, что уже есть

- Просмотри `dock/tasks/` по теме: нет ли плана, который это уже покрывает
  или с которым новый поспорит. Нашёл — дополняй **журналом** (сделанный
  план не переписывается), а не заводи параллельный.
- Прочитай целиком файлы, которые план собирается менять, и решения, на
  которые опирается. Строка в плане: «прочитано: … ; переиспользуем: …».

## 2. «За 60 секунд» — первым разделом, написанным последним

Для владельца, почти без имён файлов:
1. что сейчас плохо — на живом примере;
2. что изменится и что человек увидит после ЭТОЙ задачи;
3. почему этот вариант, его честная цена и что отвергнуто;
4. что сознательно НЕ делаем;
5. как показать результат, не читая кода.

## 3. Таблица состояний — для всего, что пишет или шлёт

Обязательна, если задача меняет базу, шлёт события, держит соединения или
повторяет. Строки — минимум эти:

| Сценарий | Что изменилось | Что увидит человек | Повтор |
|---|---|---|---|
| успех | | | |
| отказ до начала изменений | | | |
| отказ посередине | | | |
| **отказ после фиксации, до ответа или рассылки** | | | |
| повтор того же запроса | | | |
| два одновременных | | | |
| перезапуск процесса / выкладка | | | |

Строку нельзя заполнить без догадки — это вопрос владельцу, а не место для
«вероятно». 📏 Ради чего: task-093 — реплика записана, чтение после фиксации
упало, звонок не ушёл никому, и ни один план этой строки не содержал.

## 4. Каждый признак приёмки доказуем

Для каждого П- и В- пункта:
- чем воспроизводится **детерминированно**; нужна ли подделка или
  искусственный отказ, и разрешена ли она здесь;
- какой наблюдаемый исход доказывает (ответ, строка в базе, число, экран);
- **может ли проверка пройти по чужой причине** — и как это исключено
  (например, порядок запросов, а не только «реплика на экране»);
- какая поломка кода обязана её покрасить;
- проверяется настоящий артефакт (живой стек, собранный образ, SQL из
  `.toSQL()`), а не удобная копия. 📏 Прибор нагрузки шесть раз мерил
  свою копию клиента вместо клиента (task-091).

Проверку, которую сейчас поставить нельзя, так и называй — «не доказано»,
а не «готово».

## 5. Числа до кода

По `AGENTS.md`: RED по задетым дверям, цена в запросах к базе, одно SLO
строкой. Для нагрузки — сколько вкладок, какая частота, какой прибор, два
прогона, названные условия. «Быстро» и «надёжно» числами не являются.

## 6. Границы

- **Один план или два — по сути, а не по числу файлов.** Вертикальный срез
  законно задевает сервер, контракт, клиент, тест и спецификацию — это одно
  изменение. Делить, если верно хоть одно:
  1. части сдаются по отдельности, и после каждой система работает;
  2. у частей разный риск или разный арбитр.
  Если одна часть без другой ломает поведение — это не деление, а порядок:
  строка «зависит от» в обоих планах.
- **Размер — повод задуматься, а не предел.** Считаются строки продуктового
  кода, а не файлы; ориентир — около 400 изменённых. Тесты, спецификация
  и журнал не в счёт. Крупный план, который не делится, пишет в границах
  одной строкой, почему он целиком, и сдаётся с объяснением по частям:
  что с чем связано, крайние случаи, пути отказа — так же, как большой дифф
  в энциклопедии проекта (`dock/ai/!AI_main_inst.md`: «дифф больше ~400 строк —
  событие: разбить или объяснять частями»). 📏 Ради чего: счёт файлов делил срез
  по разметке, а не по смыслу — «больше семи файлов» было названо причиной
  разделения среза 2 (task-094), хотя настоящие причины были другие.
  Источник: [Google eng-practices — Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)
  («минимальное изменение, которое решает одну вещь»; «система продолжает
  работать после вливания»);
- «не трогать» — обязательно, если рядом чужая параллельная работа, старый
  путь или файлы владельца;
- для каждого файла больше ста строк в «менять» — где в нём ранние выходы,
  перехваты ошибок и эффекты, которые правка может обойти.

## 7. Сверка перед отдачей

- шаги не противоречат признакам приёмки; вопросы к тестам покрывают все
  признаки;
- все файлы, нужные для шагов, есть в границах;
- расхождения с `dock/decisions.md` названы в плане строкой, а не
  комментарием в коде;
- решение необратимо или дорого в откате (данные, протокол, права,
  зависимость) — ресёрч с источниками сделан, ссылки в плане;
- **второй взгляд:** для плана с риском «высокий» — независимый разбор
  свежим контекстом (агент `gap-finder`) до отдачи владельцу, и что из
  разбора принято или отвергнуто — в журнале плана.

## Стоп

Неясно, что станет с данными при отказе, как откатить или чем доказать —
не додумывай. Вопрос владельцу, план остаётся черновиком.
