# Fail-open и опасные значения по умолчанию

> Перенесено 27.09.2026 из audit_project (`.claude/skills/security-review/SKILL.md`),
> оставлена только методика fail-open — остальной чеклист (Django-специфика, GenericFK,
> permission_classes) в проекте не применим и выброшен.

## Ключевое различие

- **Fail-open (CRITICAL):** переменная отсутствует → приложение всё равно стартует,
  со слабым или пустым значением.
- **Fail-secure (SAFE):** переменная отсутствует → приложение падает с понятной
  ошибкой при старте, а не позже и не молча.

У нас это уже названо правилом («нет данных — понятная ошибка, а не заглушка или
выдуманное значение», `AGENTS.md`) — этот скилл даёт способ его проверить, а не
повторяет его словами.

## Наш код: как читается окружение

`backend/src/platform/config.ts` — единственное место, где бэкенд трогает
`process.env` (комментарий в файле: «Единственное место, где читается окружение»).
Ревью, нашедшее `process.env` где-то ещё в `backend/src`, — уже находка.

Три способа читать переменную там, и они не равнозначны:

```ts
// fail-secure — обязательная переменная без неё не даёт стартовать
databaseUrl: required("DATABASE_URL"),   // required() бросает Error, если пусто

// fail-open по умолчанию, но безопасно, потому что порт — не секрет
port: Number(process.env.API_PORT ?? 3000),

// fail-open ОСОЗНАННО и разобрано в комментарии рядом: значение по умолчанию —
// самое строгое (одна компания на установку), включение требует явного "true"
multiWorkspace: process.env.AMPLIFIE_MULTI_WORKSPACE === "true",
```

Строка `=== "true"` — не то же самое, что `Boolean(process.env.X)` или
`!!process.env.X`: у последних двух непустая строка `"false"` тоже даёt `true` —
это и есть fail-open в маскировке.

`tools/ops/make-env.mjs` рождает настройки настоящей установки (`make env-box`), а
не копирует образец: `.env.example` специально держит слабый пароль,
`NODE_ENV=development` и не содержит `AMPLIFIE_SECRET_KEY` — копировать его в
`.env` боевой установки нельзя, а `boxSettings()` печатает `NODE_ENV=production` и
не пишет `AMPLIFIE_MULTI_WORKSPACE` вовсе (см. паттерн 4 ниже).

## Workflow проверки

1. **SEARCH**: `grep -rn "process\.env\." backend/src --include="*.ts" | grep -v test`
   — и отдельно `grep -rn "??\|??=" ` рядом с `process.env`, чтобы найти умолчания.
2. **VERIFY**: для каждого совпадения — приложение стартует без этой переменной?
   Прочитать `required()` вокруг значения целиком, не по фрагменту.
3. **CONFIRM**: даёт ли значение по умолчанию **самое строгое** поведение
   (выключенная фича, отсутствие прав, одна компания), а не удобное для разработки?
   `tools/ops/make-env.mjs` и `compose.yml` — подтверждают ли они то же самое для
   боевого профиля, или дев-профиль (`.env.example`, `compose.dev.yml`) отличается
   ровно в опасную сторону и это названо вслух?
4. **REPORT**: файл:строка, что произойдёт без переменной, чем это доказано (трейс
   до использования, а не предположение).

## Наши примеры

| Место | Что делает | Fail-open или fail-secure |
|---|---|---|
| `backend/src/platform/config.ts:12` `required("DATABASE_URL")` | бросает `Error` при пустой переменной | fail-secure |
| `backend/src/platform/config.ts:27` `AMPLIFIE_MULTI_WORKSPACE === "true"` | без переменной — `false`, одна компания | fail-secure по умолчанию, включение требует явного слова (комментарий рядом называет это осознанно) |
| `backend/src/platform/config.ts:45` `AMPLIFIE_VERSION \|\| null` | **не** `??`: пустая строка из Dockerfile тоже даёт `null`, а не `""` | fail-secure сознательно — `??` пропустил бы пустую строку насквозь (комментарий в файле разбирает именно эту ошибку) |
| `tools/ops/make-env.mjs boxSettings()` | не пишет `AMPLIFIE_MULTI_WORKSPACE` в файл настоящей установки вовсе | правильно: «чего нет, то не переставляют „чтобы проверить“» — сильнее, чем `=false` |
| `compose.yml` (комментарий у `NODE_ENV`) | у настоящей установки нет строки разрешения многих компаний вовсе, только у `compose.dev.yml` | fail-secure — дыра была бы в обратную сторону |
| `frontend/Caddyfile` | `Content-Security-Policy`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin` на каждый ответ; исторический инцидент 2026-09-04 — инлайн-матчер `respond / "заглушка" 200` в Caddy поймал не корень, а ВСЕ пути, и приёмочный тест на вход стал зелёным без единой строки кода входа | сам заголовок безопасен; ловушка — в матчерах прокси, которые незаметно расширяют область действия |

## Config Validation (опасные значения молча)

Проверяй, что настройки не принимают опасные значения без явной валидации —
общий паттерн, не завязанный на конкретный фреймворк:

| Опасный паттерн | Почему опасно | Правильно |
|---|---|---|
| `timeout=0` → бесконечность | никогда не истекает | валидировать `timeout > 0` |
| булев флаг молча отключает проверку (`verifySsl=false` по умолчанию) | по умолчанию — дыра | значение по умолчанию — включённая проверка |
| пустая строка обходит проверку (`token=""` пропускает) | `if (token)` вместо `if (token != null)` | `if (!token) throw ...` |
| функция проверки возвращает `false` вместо `throw` на невалидном вводе | вызывающий код может забыть проверить возврат | бросать на невалидности, а не молча возвращать |

## Отговорки, которые не принимаем

| Отговорка | Почему не принимаем |
|---|---|
| «Это для разработки» | дев-код имеет свойство попадать в прод — граница держится файлом (`compose.dev.yml`), а не намерением |
| «Прод переопределяет» | докажи: покажи, где именно (`compose.yml`, `tools/ops/make-env.mjs`) и что там нет обратного пути |
| «Без конфига не запустится» | докажи трассировкой кода до использования — часто это fail-open, а не fail-secure |
| «Это за авторизацией» | эшелонированная защита: скомпрометированная сессия всё равно этим воспользуется |
